# 10b — Hai namespace qua Linux bridge

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-11-03 14:00
- Thời lượng: 40 phút
- Máy thực thi / OS / cluster context / namespace: macOS Darwin arm64 (OrbStack engine), Docker container `nfk-10b-lab` (Linux Alpine 3.24, image `nfk-07b-tools:local`, `--cap-add NET_ADMIN --cap-add SYS_ADMIN`).
- Tài nguyên lab sở hữu: Bridge `br0` (không có IPv4), namespaces `ns-a`, `ns-b`, 2 veth pairs (`veth-a` <-> `veth-a-br`, `veth-b` <-> `veth-b-br`).
- Phiên bản và tài liệu đã đối chiếu:
  - bridge(8): https://man7.org/linux/man-pages/man8/bridge.8.html
  - ip-link(8) bridge type: https://man7.org/linux/man-pages/man8/ip-link.8.html
  - Kubernetes Flannel / CNI bridge networking: https://github.com/flannel-io/flannel
- Phạm vi được phép thay đổi: Container `nfk-10b-lab`, bridge `br0`, namespaces `ns-a`, `ns-b`.

## Mục tiêu

- Dựng topology 2 namespace nối qua một Linux Bridge: `ns-a` ↔ `veth-a` ↔ `veth-a-br` ↔ `br0` ↔ `veth-b-br` ↔ `veth-b` ↔ `ns-b`.
- Giải thích cơ chế chuyển tiếp Tầng 2 (L2 switching), ARP broadcast và bảng Forwarding Database (FDB).
- Kiểm chứng thực tế: **Linux Bridge là thiết bị L2 thuần túy, không cần địa chỉ IP để chuyển tiếp dữ liệu giữa 2 Pod trong cùng subnet**.
- Phân biệt sự khác nhau giữa L2 Switch (Bridge) và L3 Router.
- Bóc tách sự cố thực tế: Interface bên trong Pod vẫn `UP` nhưng mất kết nối do đầu dây phía Node bị tuột khỏi Bridge (`master br0`).

## Các bước thực hành / câu lệnh

Học viên trực tiếp thực thi trên terminal macOS qua Docker CLI:

```bash
# 1. Khởi tạo container lab
docker run -d --name nfk-10b-lab --cap-add NET_ADMIN --cap-add SYS_ADMIN nfk-07b-tools:local sleep infinity

# 2. Tạo Bridge br0 và 2 network namespace
docker exec nfk-10b-lab ip link add br0 type bridge
docker exec nfk-10b-lab ip link set br0 up
docker exec nfk-10b-lab ip netns add ns-a
docker exec nfk-10b-lab ip netns add ns-b

# 3. Tạo 2 veth pairs và cắm vào Bridge qua master br0
docker exec nfk-10b-lab ip link add veth-a type veth peer name veth-a-br
docker exec nfk-10b-lab ip link add veth-b type veth peer name veth-b-br
docker exec nfk-10b-lab ip link set veth-a netns ns-a
docker exec nfk-10b-lab ip link set veth-b netns ns-b
docker exec nfk-10b-lab ip link set veth-a-br master br0
docker exec nfk-10b-lab ip link set veth-a-br up
docker exec nfk-10b-lab ip link set veth-b-br master br0
docker exec nfk-10b-lab ip link set veth-b-br up

# 4. Gán IP cho 2 namespace (không gán IP cho br0) và bật UP
docker exec nfk-10b-lab ip netns exec ns-a ip addr add 10.100.2.1/24 dev veth-a
docker exec nfk-10b-lab ip netns exec ns-a ip link set veth-a up
docker exec nfk-10b-lab ip netns exec ns-a ip link set lo up
docker exec nfk-10b-lab ip netns exec ns-b ip addr add 10.100.2.2/24 dev veth-b
docker exec nfk-10b-lab ip netns exec ns-b ip link set veth-b up
docker exec nfk-10b-lab ip netns exec ns-b ip link set lo up

# 5. Kiểm tra br0 không có IPv4 và ping thử nghiệm
docker exec nfk-10b-lab ip -br addr show br0
docker exec nfk-10b-lab ip netns exec ns-a ping -c 2 10.100.2.2

# 6. Quan sát bảng ARP và FDB
docker exec nfk-10b-lab ip netns exec ns-a ip neigh
docker exec nfk-10b-lab bridge fdb show br br0

# 7. Khởi chạy HTTP server và đo kiểm L7
docker exec -d nfk-10b-lab ip netns exec ns-a python3 -m http.server 8080
docker exec nfk-10b-lab ip netns exec ns-b curl -s -I http://10.100.2.1:8080/ | head -n 1
```

## Bằng chứng thực tế thu thập được

1. **Bridge không có địa chỉ IPv4:**
   ```text
   br0              UP             fe80::38d0:ebff:fec3:1394/64
   ```
2. **Ping L3 thành công mỹ mãn qua Bridge không có IP:**
   ```text
   PING 10.100.2.2 (10.100.2.2): 56 data bytes
   64 bytes from 10.100.2.2: seq=0 ttl=64 time=0.154 ms
   64 bytes from 10.100.2.2: seq=1 ttl=64 time=0.135 ms
   2 packets transmitted, 2 packets received, 0% packet loss
   ```
3. **Bảng ARP và FDB xác nhận cơ chế L2:**
   - Trong `ns-a`: `10.100.2.2 dev veth-a lladdr 7e:89:df:14:5a:59 STALE` (đã phân giải IP đích sang MAC).
   - Trên Bridge `br0`: Bảng FDB ánh xạ MAC tới cổng `veth-a-br` và `veth-b-br`.
4. **Kết nối L7 HTTP:**
   ```text
   HTTP/1.0 200 OK
   ```

## Lỗi gặp phải và phân tích root cause (Break & Fix)

| Triệu chứng | Giả thuyết | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| `ns-b` curl sang `10.100.2.1:8080` bị Timeout | Dịch vụ chết, link trong Pod DOWN, hoặc tuột cổng ngoài Node | Chạy `ip -br addr` trong Pod B và `bridge link` trên Node | Trong Pod B `veth-b` vẫn UP và có IP đầy đủ; nhưng `bridge link` trên Node mất hẳn cổng `veth-b-br` |

**Phân tích kỹ thuật (Root Cause):**
Đầu dây `veth-b-br` phía Node bị gỡ khỏi Bridge (`nomaster`). Mặc dù bên trong Pod B card mạng vẫn báo `UP`, dữ liệu gửi ra ngoài bị rơi vào black hole vì không có thiết bị switch nào tiếp nhận để chuyển tiếp.

## Cách sửa và bằng chứng xác minh

- Lệnh sửa tối thiểu:
  ```bash
  docker exec nfk-10b-lab ip link set veth-b-br master br0
  ```
- Bằng chứng phục hồi:
  - Cổng `veth-b-br` xuất hiện trở lại trên `br0` với trạng thái `forwarding`:
    ```text
    4: veth-a-br@if5: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br0 state forwarding priority 32 cost 2 
    6: veth-b-br@if7: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br0 state forwarding priority 32 cost 2 
    ```
  - Kết nối HTTP phục hồi ngay lập tức:
    ```text
    HTTP/1.0 200 OK
    ```

## Review và tự giải thích

- **3 điều hiểu được:**
  1. Linux Bridge hoạt động như một Switch L2 ảo: chuyển tiếp Ethernet Frame theo bảng địa chỉ MAC (FDB).
  2. Bridge hoàn toàn KHÔNG cần có IP để chuyển tiếp traffic giữa các Pod trong cùng subnet.
  3. Khi một Pod nhìn bên trong vẫn UP nhưng không thể kết nối, nguyên nhân có thể do đầu dây `veth` phía Node bị tuột khỏi Bridge (`master br0`).
- **Giới hạn của Bridge:** Bridge chỉ làm việc ở L2 trong cùng một Broadcast Domain / subnet. Nó không thể tự định tuyến giữa 2 subnet khác nhau (cần L3 Router - bài 11a).
