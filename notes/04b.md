# 04b — Khoanh vùng lỗi routing và Checkpoint 1 (CP1)

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-10-25 17:10–19:25
- Thời lượng: 40 phút
- Máy thực thi / OS / cluster context / namespace: Windows 11 host (`LAPTOP-G35HS1Q6`), Docker Desktop Engine (`desktop-linux`), container `nfk-04b-troubleshoot` (`10.240.40.50/24`) trên bridge network `nfk-04b` (`10.240.40.0/24`). Học viên tự mở PowerShell chạy các lệnh chẩn đoán và khắc phục.
- Phiên bản và tài liệu đã đối chiếu: Ubuntu 24.04 LTS, iproute2 6.1.0, Docker Engine 29.7.2.
- Phạm vi được phép thay đổi: Container và network cô lập `nfk-04b`.

## Mục tiêu

- Sử dụng `ip route get` (L3) và `ip neigh` (L2) để phân biệt chính xác lỗi chọn đường định tuyến với lỗi phân giải địa chỉ MAC của next hop.
- Nhận diện và xử lý sự cố thực tế: Hiện tượng Route Shadowing / Blackholing khi một route cụ thể che khuất default route.
- Hoàn thành đầy đủ các tiêu chí của Cổng đánh giá Checkpoint 1 (CP1).

## Dự đoán trước lab

| Phép thử / Câu hỏi | Dự đoán của học viên | Phân tích & Thực tế đối chứng |
|---|---|---|
| Khi route cụ thể bị lỗi next hop, kernel có tự động fallback về default route không? | Dự đoán ban đầu: Có fallback | Thực tế: **KHÔNG**. Kernel Linux thực hiện deterministic LPM lookup: khi prefix cụ thể hơn đã khớp, kernel chốt route đó và chuyển xuống L2. Nếu next hop không phản hồi ARP, gói tin bị DROP ngay lập tức (Route Shadowing), không bao giờ tự quay lại thử default route. |
| Lệnh phân biệt lỗi L3 và L2 | Tầng L3 là `ip route`, L2 là cache | Chính xác: L3 dùng `ip route get <IP>` để xem quyết định next hop/interface; L2 dùng `ip neigh` để xem trạng thái cache phân giải MAC của next hop (`REACHABLE`, `STALE`, hay `FAILED`). |

## Các bước thực hành do học viên tự thực hiện trên PowerShell

### 1. Thu thập bằng chứng ban đầu (Baseline & Triệu chứng)
- Ping đối chứng:
  ```powershell
  docker exec nfk-04b-troubleshoot ping -c 2 -W 2 1.1.1.1
  # Kết quả: 0% packet loss (thành công)
  docker exec nfk-04b-troubleshoot ping -c 2 -W 2 8.8.8.8
  # Kết quả: 100% packet loss (thất bại)
  ```
- Kiểm tra L3 routing decision:
  ```powershell
  docker exec nfk-04b-troubleshoot ip route get 8.8.8.8
  # Output: 8.8.8.8 via 10.240.40.210 dev eth0 src 10.240.40.50 uid 0
  ```
- Kiểm tra L2 neighbor state:
  ```powershell
  docker exec nfk-04b-troubleshoot ip neigh
  # Output:
  # 10.240.40.1 dev eth0 lladdr 0a:7e:6c:d8:cc:a7 STALE 
  # 10.240.40.210 dev eth0 FAILED 
  ```
- Đọc routing table:
  ```powershell
  docker exec nfk-04b-troubleshoot ip route
  # default via 10.240.40.1 dev eth0 
  # 8.8.8.0/24 via 10.240.40.210 dev eth0 
  # 10.240.40.0/24 dev eth0 proto kernel scope link src 10.240.40.50 
  ```

### 2. Xác định nguyên nhân gốc (Root Cause)
- Học viên chỉ ra chính xác:
  - Route `8.8.8.0/24` cụ thể hơn default route `/0` nên bắt cóc traffic đi `8.8.8.8`.
  - Next hop `10.240.40.210` không tồn tại, khiến `ip neigh` báo `FAILED` (lỗi L2 ARP failure).
  - Gói tin tới `1.1.1.1` không khớp `/24` nên đi qua `default via 10.240.40.1` bình thường.

### 3. Sửa lỗi tối thiểu và kiểm chứng sau sửa (Post-fix verification)
- Thực hiện xóa route lỗi:
  ```powershell
  docker exec nfk-04b-troubleshoot ip route del 8.8.8.0/24
  ```
- Kết quả kiểm chứng:
  - `ip route get 8.8.8.8`: đã chuyển về `via 10.240.40.1 dev eth0` (default route chuẩn).
  - `ping 8.8.8.8`: 2 packets transmitted, 2 received, 0% packet loss (thành công).
  - `ping 1.1.1.1`: luồng đối chứng vẫn 0% packet loss.
  - Bảng route trở về trạng thái sạch sẽ.

## Đánh giá Checkpoint 1 (CP1)

Học viên đã hoàn thành và vượt qua toàn bộ 4 tiêu chí của CP1:

1. **Subnet Membership (`172.16.10.70/26`):**
   - Tính đúng Network IP `172.16.10.64`, Broadcast IP `172.16.10.127`, dải khả dụng `.65–.126`.
   - Phân loại đúng: Host 2 (`.65`) & Host 3 (`.120`) cùng subnet; Host 1 (`.60`) & Host 4 (`.130`) khác subnet.
2. **Next hop, End-to-end IP vs Hop-by-hop MAC:**
   - Đã hiểu rõ: IP Header (L3) giữ nguyên Destination IP của máy đích cuối cùng (`172.16.10.130`).
   - Ethernet Header (L2) ghi Destination MAC của Gateway trung gian (`172.16.10.65`).
3. **Bằng chứng L2/L3:**
   - Đã dùng `ip route get` và `ip neigh` (FAILED) trên lab thực tế để bắt bệnh.
4. **3 lý do mất kết nối dù IP hợp lệ:**
   - (1) Firewall / Security Group / iptables DROP traffic.
   - (2) Gateway / Next hop die (L2 ARP FAILED).
   - (3) Route shadowing / blackhole route trỏ sai next hop (hoặc thiếu return route chiều về).

## Rollback và Dọn dẹp

- Đã xóa container `nfk-04b-troubleshoot`: `docker rm -f nfk-04b-troubleshoot` (thành công).
- Đã xóa network `nfk-04b`: `docker network rm nfk-04b` (thành công).
- Xác minh sạch sẽ, không còn tài nguyên tồn đọng.
