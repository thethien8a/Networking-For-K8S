# 13a — Từ container namespace đến mạng dùng chung của Pod

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-11-05 00:10
- Thời lượng: 35 phút
- Máy thực thi / OS / cluster context / namespace: macOS Darwin arm64 / k3d cluster `de-k3d` (v1.33.6+k3s1) / context `k3d-de-k3d` / namespace `nfk-13a`
- Phiên bản và tài liệu đã đối chiếu: Kubernetes Pod Network Concept (https://kubernetes.io/docs/concepts/workloads/pods/#pod-networking)
- Phạm vi được phép thay đổi: namespace `nfk-13a` trên cluster `de-k3d`

## Mục tiêu

- Ánh xạ kiến thức Linux Network Namespace (Module 10) sang container và Kubernetes Pod.
- Chứng minh hai container trong cùng Pod dùng chung `localhost` (`127.0.0.1`) và chia sẻ chung không gian port (port space).
- Chứng minh ranh giới cô lập loopback giữa các Pod độc lập và chứng minh vai trò của `containerPort` chỉ là metadata.

## Dự đoán trước lab

| Phép thử | Kết quả dự đoán | Vì sao / giả định |
|---|---|---|
| Container client gọi `127.0.0.1:8080` tới server trong cùng Pod | Thành công | Hai container cùng Pod chia sẻ chung loopback interface `lo` trong cùng Network Namespace. |
| Hai container trong cùng Pod cùng bind port `8080` | Container thứ 2 không khởi động được | Hai container chia sẻ chung không gian port, kernel báo xung đột port. |
| Pod độc lập bên ngoài gọi `127.0.0.1:8080` | Không thành công | Loopback `127.0.0.1` bị cô lập trong Network Namespace riêng của từng Pod. |

## Topology và địa chỉ IP

```
Node: k3d-de-k3d-agent-0
├── Pod: pod-shared-net (Netns riêng của Pod, IP: 10.42.3.13)
│   ├── Loopback: lo (127.0.0.1)
│   ├── Interface: eth0@if9 (veth pair nối ra node)
│   ├── Container "server" (python:3.12-alpine): LISTEN 0.0.0.0:8080
│   └── Container "client" (curlimages/curl:latest): curl 127.0.0.1:8080 (OK)
│
└── Pod: pod-isolated-client (Netns riêng độc lập, IP: 10.42.3.14)
    ├── Loopback: lo (127.0.0.1) -> curl 127.0.0.1:8080 -> Connection refused (Exit 7)
    └── Gọi qua Pod IP: curl 10.42.3.13:8080 -> 200 OK (qua veth pair & node routing)
```

## Các bước thực hành / câu lệnh

```bash
# 1. Tạo Pod đa container pod-shared-net (không khai báo containerPort)
kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: pod-shared-net
  namespace: nfk-13a
spec:
  containers:
  - name: server
    image: python:3.12-alpine
    command: ["sh", "-c", "python3 -m http.server 8080"]
  - name: client
    image: curlimages/curl:latest
    command: ["sh", "-c", "sleep 3600"]
EOF

# 2. Kiểm tra IP & interface từ container client
kubectl exec -n nfk-13a pod-shared-net -c client -- ip addr

# 3. Kiểm tra socket listening từ container client
kubectl exec -n nfk-13a pod-shared-net -c client -- netstat -tlpn

# 4. Kiểm tra curl localhost & Pod IP từ client
kubectl exec -n nfk-13a pod-shared-net -c client -- curl -s -I http://127.0.0.1:8080
kubectl exec -n nfk-13a pod-shared-net -c client -- curl -s -I http://10.42.3.13:8080

# 5. Tạo Pod độc lập pod-isolated-client
kubectl run pod-isolated-client -n nfk-13a --image=curlimages/curl:latest --command -- sleep 3600

# 6. Thử nghiệm kết nối từ pod-isolated-client
kubectl exec -n nfk-13a pod-isolated-client -- curl -v --connect-timeout 2 http://127.0.0.1:8080
kubectl exec -n nfk-13a pod-isolated-client -- curl -s -I http://10.42.3.13:8080

# 7. Thử nghiệm xung đột port
kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: pod-port-collision
  namespace: nfk-13a
spec:
  containers:
  - name: web-app-1
    image: python:3.12-alpine
    command: ["sh", "-c", "python3 -m http.server 8080"]
  - name: web-app-2
    image: python:3.12-alpine
    command: ["sh", "-c", "python3 -m http.server 8080"]
EOF

# 8. Xem lỗi xung đột port
kubectl get pod pod-port-collision -n nfk-13a
kubectl logs pod-port-collision -c web-app-2 -n nfk-13a
```

## Bằng chứng

1. **Chung Network Namespace trong Pod:**
   - Interface `eth0@if9` có IP `10.42.3.13/24`.
   - `netstat -tlpn` trong container `client` thấy socket `0.0.0.0:8080` của container `server` (cột PID là `-` vì khác PID namespace nhưng chung Network namespace).
   - `curl http://127.0.0.1:8080` trả về `HTTP/1.0 200 OK`.
   - `curl http://10.42.3.13:8080` trả về `HTTP/1.0 200 OK`.
   - Cả hai hoạt động hoàn hảo dù manifest KHÔNG hề khai báo `containerPort: 8080`.

2. **Cô lập Loopback giữa các Pod:**
   - Từ `pod-isolated-client`, `curl http://127.0.0.1:8080` trả về ngay lập tức: `curl: (7) Failed to connect to 127.0.0.1:8080: Connection refused`.
   - Từ `pod-isolated-client`, `curl http://10.42.3.13:8080` thành công trả về `HTTP/1.0 200 OK`.

3. **Xung đột Port Space:**
   - Pod `pod-port-collision` ở trạng thái `1/2 CrashLoopBackOff`.
   - Container `web-app-2` crash với lỗi: `OSError: [Errno 98] Address in use` tại hàm `socket.bind()`.

## Lỗi gặp phải và phân tích root cause

| Triệu chứng | Giả thuyết | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| `pod-port-collision` ở trạng thái `CrashLoopBackOff` | Container thứ 2 xung đột port 8080 với container 1 | `kubectl logs pod-port-collision -c web-app-2` | Log xác nhận `OSError: [Errno 98] Address in use`. |
| `pod-isolated-client` curl `127.0.0.1:8080` bị `Connection refused` | Loopback `127.0.0.1` thuộc netns riêng của pod-isolated-client | So sánh với `curl http://10.42.3.13:8080` | Gói tin loopback không ra ngoài netns, trong khi gọi Pod IP qua veth pair thì thành công `200 OK`. |

## Cách sửa và bằng chứng xác minh

- Tránh xung đột port trong Pod: cấu hình mỗi container lắng nghe trên một port khác nhau (ví dụ: app nghe 8080, sidecar metrics exporter nghe 9091).
- Giao tiếp giữa các Pod khác nhau: luôn sử dụng Pod IP hoặc Kubernetes Service / DNS, không dùng `localhost`.

## Rollback / dọn dẹp / tài nguyên còn giữ

- Xóa namespace `nfk-13a` cùng tất cả Pod thử nghiệm (`pod-shared-net`, `pod-isolated-client`, `pod-port-collision`):
  `kubectl delete namespace nfk-13a`
- Kiểm tra lại: Không còn tài nguyên rác tồn đọng.

## Review và tự giải thích

- 3 điều hiểu được:
  1. Pod là tập hợp các container chia sẻ chung một Linux Network Namespace duy nhất (khởi tạo bởi pause/infra container).
  2. Giao tiếp qua `localhost` (`127.0.0.1`) giữa các container trong cùng Pod có độ trễ cực thấp (zero-hop qua `lo`), là nền tảng của Sidecar pattern trong Kubernetes. Loopback không thể vượt qua ranh giới giữa 2 Pod khác nhau.
  3. Tất cả container trong Pod chia sẻ chung không gian port (port space) nên không thể bind trùng port. Trường `containerPort` trong manifest chỉ là metadata tài liệu, không mở port hay can thiệp vào tầng kernel.
- 2 điều còn thắc mắc:
  1. Khi một container trong Pod bind `127.0.0.1` thay vì `0.0.0.0`, các Pod khác ở ngoài có truy cập được qua Pod IP không? (Nội dung của bài 13b).
  2. Khi dùng `hostNetwork: true`, Pod sẽ dùng chung namespace với Node như thế nào?
- 1 thử nghiệm tiếp theo: Khảo sát bind address (`127.0.0.1` vs `0.0.0.0`) và `hostNetwork: true` trong [13b](13b-bind-address-va-hostnetwork.md).
- Câu áp dụng sang tình huống khác và câu trả lời:
  - Tình huống: Trong Spark on K8s, sidecar container Prometheus Exporter scrape metrics từ Spark Driver container qua interface nào?
  - Trả lời: Scrape trực tiếp qua `http://127.0.0.1:<port>` nội bộ trong Pod, không cần tạo Service hay gọi qua Pod IP.
- Mức gợi ý cao nhất: Hint 1 (Định hướng).
