# 23a — LoadBalancer bare-metal: cấp IP khác với quảng bá IP

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-11-12 16:17
- Thời lượng: 40 phút
- Máy thực thi / OS / cluster context / namespace:
  - macOS host: Darwin arm64 (Client)
  - k3d cluster: `k3d-de-k3d`, K3s v1.33.6+k3s1 (3 nodes: `server-0`, `agent-0`, `agent-1`)
  - Docker network: `k3d-de-k3d` (Subnet `192.168.155.0/24`, Gateway `192.168.155.1`)
  - LoadBalancer Controller hiện tại: K3s built-in Klipper-LB (`k3s-servicelb`)
- Phiên bản và tài liệu đã đối chiếu:
  - Kubernetes Service Type LoadBalancer: https://kubernetes.io/docs/concepts/services-networking/service/#loadbalancer
  - K3s ServiceLB (Klipper-LB): https://docs.k3s.io/networking#service-load-balancer
  - MetalLB Architecture & Concepts: https://metallb.universe.tf/concepts/
- Phạm vi được phép thay đổi: Không thay đổi tài nguyên cụm; khảo sát read-only Service và Pods trong `kube-system` và `docker network`.

## Mục tiêu

- Hiểu vì sao `type: LoadBalancer` cần implementation / controller tích hợp riêng ngoài việc tạo đối tượng YAML trên API Server.
- Phân biệt rạch ròi 3 điều kiện độc lập: Allocation (Cấp IP), Advertisement / Reachability (Quảng bá IP / định tuyến), và Backend forwarding (kube-proxy / iptables).
- Khảo sát hiện trạng LoadBalancer trên cụm lab k3d (Klipper-LB) và lập Checklist tính khả thi (Feasibility Checklist) cho MetalLB L2 trước bài 23b.
- Xây dựng Mental Model chẩn đoán sự cố: Bóc tách lỗi Tầng 2 (L2 ARP / Connect Timeout) vs Lỗi Tầng 3/4 (TCP RST / Connection Refused tức thì).

## Dự đoán trước lab

| Phép thử | Kết quả dự đoán | Vì sao / giả định |
|---|---|---|
| Service có external IP nhưng client ở ngoài L2/route hỗ trợ | Gói tin thất bại (Timeout) | Nếu cùng subnet mà không có ARP Reply thì ARP cache FAILED -> Timeout; nếu khác subnet mà router không có route thì router DROP -> Timeout / Host Unreachable. |
| Cấp được IP và chạm tới Node có bảo đảm ứng dụng trả 200 OK? | Không bảo đảm | Tầng 1 và 2 chỉ đưa gói tin tới Node. Tầng 3 (Service selector, EndpointSlice, targetPort, Pod crash) vẫn có thể gây lỗi Connection Refused hoặc HTTP 5xx. |
| K8s bare-metal không có controller thì Service type LoadBalancer hiện gì? | `<pending>` ở EXTERNAL-IP | K8s core không quản lý mạng vật lý bên ngoài nên không tự sinh IP; cần controller bên ngoài cập nhật `status.loadBalancer.ingress`. |

## Các bước thực hành / câu lệnh

1. Khảo sát danh sách Service toàn cụm:
   ```bash
   kubectl --context k3d-de-k3d get svc -A
   # Quan sát: Service kube-system/traefik có TYPE LoadBalancer, EXTERNAL-IP gán cả 3 IP Node.
   ```
2. Khảo sát các Pod LoadBalancer trong kube-system:
   ```bash
   kubectl --context k3d-de-k3d get pods -n kube-system -o wide
   # Quan sát: Các Pod svclb-traefik-* chạy trên từng Node (Klipper-LB).
   ```
3. Khảo sát Docker bridge network của k3d:
   ```bash
   docker network inspect k3d-de-k3d --format '{{json .IPAM.Config}}'
   # Subnet: 192.168.155.0/24, Gateway: 192.168.155.1.
   ```

## Checklist tính khả thi MetalLB L2 (Feasibility Checklist)

| Hạng mục | Hiện trạng lab k3d | Đánh giá & Rủi ro | Giải pháp cho bài 23b |
|---|---|---|---|
| **Nguồn IP Pool** | Subnet `192.168.155.0/24` | MetalLB L2 cần IP cùng L2 broadcast domain để trả lời ARP. | Chọn dải IP tĩnh chưa dùng: `192.168.155.240-192.168.155.250`. |
| **Tránh trùng IP (Collision)** | Docker IPAM cấp từ `.2` trở lên | Nếu trùng IP sẽ gây ARP Flapping làm chập chờn kết nối. | Dải `.240-.250` nằm ở cuối subnet, không bị Docker IPAM cấp động. |
| **Quảng bá L2 (ARP/GARP)** | Chạy trong Docker bridge `k3d-de-k3d` | MetalLB Speaker dùng ARP/GARP. Nếu client ở ngoài L3 hop (macOS), gói ARP không qua được router trừ khi có proxy-arp hoặc client nằm cùng bridge. | Sẽ kiểm chứng vị trí client: test từ macOS vs test từ một container client nằm trực tiếp trong network `k3d-de-k3d`. |
| **Xung đột Klipper-LB** | Klipper-LB đang quản lý ServiceLB | Cả Klipper và MetalLB cùng tranh giành Service type LoadBalancer. | Khi test MetalLB ở 23b, cần chỉ định `loadBalancerClass` hoặc tắt/cấu hình riêng cho Service bài học. |

## Phân tích hai giả thuyết chẩn đoán sự cố

| Giả thuyết | Tầng mạng | Dấu hiệu nhận biết trên Client | Bảng ARP (`arp -n <IP>`) |
|---|---|---|---|
| **Giả thuyết A: Lỗi External Reachability** | Layer 2 (ARP / Mạng ngoài / Routing) | `Connect Timeout` (treo 2–5s rồi timeout), hoặc `No route to host` | `(incomplete)` hoặc `FAILED` |
| **Giả thuyết B: Lỗi Backend Data Plane** | Layer 3/4 (Service / Kube-proxy / Pod) | `Connection refused` tức thì (trong 0.001s do nhận cờ TCP RST từ Node) | Có địa chỉ MAC hợp lệ của Node |

## Rollback / dọn dẹp / tài nguyên còn giữ

- Bài 23a là bài khảo sát kiến trúc và mental model, không tạo hoặc sửa đổi tài nguyên nào trong cụm k3d.
- Không có tài nguyên rác hoặc nợ rollback. Cụm k3d ở trạng thái sạch và sẵn sàng cho bài 23b.

## Review và tự giải thích

- **3 điều hiểu được:**
  1. `type: LoadBalancer` trên Bare-metal không tự cấp được IP vì K8s core không quản lý hạ tầng mạng LAN/VLAN bên ngoài; cần controller riêng (MetalLB hoặc Klipper).
  2. Klipper-LB của K3s chỉ lấy IP của các Node gán vào Service, trong khi MetalLB cấp Virtual IP (VIP) thực thụ từ IP Pool tĩnh.
  3. Phân biệt bóc tách sự cố: Timeout + ARP incomplete là lỗi mạng ngoài/L2; Connection Refused tức thì + có MAC là lỗi nội bộ K8s backend (targetPort/selector).
- **2 điều còn thắc mắc:**
  1. Khi macOS đứng ở ngoài (qua L3 hop TTL=63), bản tin L2 GARP của MetalLB có chạm tới được macOS không hay phải test qua bridge container?
  2. Cách MetalLB và Klipper-LB cùng tồn tại trong một cụm mà không tranh chấp Service.
- **1 thử nghiệm tiếp theo:** Triển khai MetalLB ở bài [23b](lesson/23b-metallb-feasibility-lab.md) và đo kiểm thực tế việc cấp phát VIP và quảng bá ARP.
