# 13b — Bind address của Pod và trường hợp hostNetwork

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-11-05
- Thời lượng: 40 phút
- Máy thực thi / OS / cluster context / namespace: macOS Darwin arm64 / k3d cluster `de-k3d` (context `k3d-de-k3d`), namespace `nfk-13b`
- Phiên bản và tài liệu đã đối chiếu: Kubernetes v1.33.6+k3s1, containerd 2.1.5-k3s1.33
- Phạm vi được phép thay đổi: Namespace lab `nfk-13b`

## Mục tiêu

- Debug và kiểm chứng sự khác biệt giữa bind loopback (`127.0.0.1`) và bind wildcard (`0.0.0.0`) trong Pod.
- Thực chứng hành vi `Connection refused` khi gọi Pod IP từ bên ngoài lẫn từ bên trong Pod nếu server bind `127.0.0.1`.
- Kiểm chứng cơ chế `hostNetwork: true`: Pod dùng chung Root Network Namespace của Node, mang IP của Node (`192.168.155.5`), nhìn thấy toàn bộ card mạng của Node (`cni0`, `flannel.1`, veth pairs).
- Phân biệt ranh giới mạng giữa Container, Pod, Node và máy Mac (Darwin).

## Dự đoán trước lab

| Phép thử | Kết quả dự đoán | Vì sao / giả định |
|---|---|---|
| Server bind `127.0.0.1:8080`, sidecar cùng Pod gọi `http://127.0.0.1:8080` | `200 OK` | Cùng dùng chung interface `lo` và socket table của Pod |
| Server bind `127.0.0.1:8080`, client khác Pod gọi `http://<Pod-IP>:8080` | `Connection refused` | Socket chỉ đón nhận traffic trên `lo`, không đón trên `eth0` |
| Bật `hostNetwork: true`, `ip addr` trong Pod hiển thị IP nào | IP của Node | Pod nhảy vào Root Network Namespace của Node thay vì CNI namespace riêng |
| "Localhost của Node" có là localhost của Mac không | Không | Node k3d là container Docker chạy trên Mac; localhost của Node chỉ là localhost trong container Node |

## Các bước thực hành / câu lệnh

### Bước 1: Deploy Pod Server bind loopback và External Client
```bash
kubectl create namespace nfk-13b
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: pod-server-loopback
  namespace: nfk-13b
spec:
  containers:
  - name: backend
    image: python:3.12-slim
    command: ["python3", "-m", "http.server", "8080", "--bind", "127.0.0.1"]
  - name: sidecar
    image: curlimages/curl:8.10.1
    command: ["sleep", "3600"]
---
apiVersion: v1
kind: Pod
metadata:
  name: pod-external-client
  namespace: nfk-13b
spec:
  containers:
  - name: client
    image: curlimages/curl:8.10.1
    command: ["sleep", "3600"]
EOF
```

### Bước 2: Đo đạc ma trận 4 trường hợp (Matrix)
```bash
# Test 1: Sidecar gọi 127.0.0.1
kubectl exec -n nfk-13b pod-server-loopback -c sidecar -- curl -s -I http://127.0.0.1:8080 | head -n 1
# Test 2: Sidecar gọi chính Pod IP (10.42.3.16)
kubectl exec -n nfk-13b pod-server-loopback -c sidecar -- curl -v --connect-timeout 2 http://10.42.3.16:8080
# Test 3: External Pod gọi 127.0.0.1
kubectl exec -n nfk-13b pod-external-client -c client -- curl -v --connect-timeout 2 http://127.0.0.1:8080
# Test 4: External Pod gọi Pod IP (10.42.3.16)
kubectl exec -n nfk-13b pod-external-client -c client -- curl -v --connect-timeout 2 http://10.42.3.16:8080
```

### Bước 3: Sửa bind sang `0.0.0.0` và đo đối chứng
```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: pod-server-wildcard
  namespace: nfk-13b
spec:
  containers:
  - name: backend
    image: python:3.12-slim
    command: ["python3", "-m", "http.server", "8080", "--bind", "0.0.0.0"]
  - name: sidecar
    image: curlimages/curl:8.10.1
    command: ["sleep", "3600"]
EOF
```
Đo kiểm đối chứng Test A, B, C đều trả về `HTTP/1.0 200 OK`.

### Bước 4: Khởi tạo Pod `hostNetwork: true` và khảo sát
```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: pod-hostnetwork
  namespace: nfk-13b
spec:
  hostNetwork: true
  nodeName: k3d-de-k3d-agent-0
  containers:
  - name: inspector
    image: curlimages/curl:8.10.1
    command: ["sleep", "3600"]
EOF
```

## Bằng chứng

### 1. Ma trận kết nối khi server bind `127.0.0.1`:
- Test 1 (Sidecar gọi `127.0.0.1`): `HTTP/1.0 200 OK`
- Test 2 (Sidecar gọi chính Pod IP `10.42.3.16`): `* connect to 10.42.3.16 port 8080 from 10.42.3.16 port 57182 failed: Connection refused`
- Test 3 (External Pod gọi `127.0.0.1`): `* connect to 127.0.0.1 port 8080 from 127.0.0.1 port 45024 failed: Connection refused`
- Test 4 (External Pod gọi Pod IP `10.42.3.16`): `* connect to 10.42.3.16 port 8080 from 10.42.1.16 port 39674 failed: Connection refused`

### 2. Kết nối sau khi đổi sang `--bind 0.0.0.0` (Pod IP: `10.42.1.17`):
- Test A (Sidecar gọi `127.0.0.1`): `HTTP/1.0 200 OK`
- Test B (Sidecar gọi Pod IP `10.42.1.17`): `HTTP/1.0 200 OK`
- Test C (External Pod gọi Pod IP `10.42.1.17`): `HTTP/1.0 200 OK`

### 3. Khảo sát Pod `hostNetwork: true`:
- Pod IP hiển thị trong `kubectl get pod`: `192.168.155.5` (trùng khớp hoàn toàn với IP của Node `k3d-de-k3d-agent-0`).
- Lệnh `ip addr` trong `pod-hostnetwork` thấy:
  - `eth0@if68`: `192.168.155.5/24` (card mạng thật của Node)
  - `flannel.1`: `10.42.3.0/32` (VXLAN interface của Node)
  - `cni0`: `10.42.3.1/24` (CNI bridge)
  - Các host veth pairs (`veth896809be@eth0`, `veth8c710800@eth0`, `veth190aeae1@eth0`, `veth2889ece4@eth0`...) nối tới các Pod khác trên Node.

## Lỗi gặp phải và phân tích root cause

| Triệu chứng | Giả thuyết | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| Sidecar curl `127.0.0.1` được 200 OK, nhưng Pod khác curl Pod IP bị `Connection refused` | Ứng dụng bind `127.0.0.1` thay vì `0.0.0.0` | Kiểm tra listener socket bằng `ss -tlpn` hoặc so sánh curl `127.0.0.1` vs curl Pod IP | Kết luận: Không phải lỗi CNI hay veth pair; đường truyền L2/L3 hoàn toàn thông nên kernel mới phản hồi `TCP RST` (Connection refused) tức thì. Root cause là socket chỉ bind trên loopback. |

## Cách sửa và bằng chứng xác minh

- Chuyển bind address của tiến trình từ `127.0.0.1` sang `0.0.0.0` (wildcard).
- Xác minh: Cả 3 hướng kết nối (localhost, Pod IP từ chính Pod, Pod IP từ Pod khác) đều trả về `200 OK`.

## Rollback / dọn dẹp / tài nguyên còn giữ

- Lệnh thực thi: `kubectl delete namespace nfk-13b`
- Kết quả kiểm tra: Namespace `nfk-13b` đã được xóa hoàn toàn cùng toàn bộ Pod (`pod-server-loopback`, `pod-external-client`, `pod-server-wildcard`, `pod-hostnetwork`). Cluster sạch sẽ, không còn tài nguyên treo.

## Review và tự giải thích

- 3 điều hiểu được:
  1. Khi bind `127.0.0.1`, chỉ có traffic gửi đến loopback mới được phục vụ; traffic đến Pod IP (trên `eth0`) bị kernel từ chối bằng `TCP RST` (`Connection refused`), kể cả khi gói tin xuất phát từ chính container trong cùng Pod.
  2. Muốn phục vụ traffic từ bên ngoài Pod (Service, Ingress, Pod khác), ứng dụng bắt buộc phải bind vào wildcard `0.0.0.0`.
  3. `hostNetwork: true` đưa Pod vào thẳng Root Network Namespace của Node, chia sẻ IP của Node và toàn bộ card mạng (`cni0`, `flannel.1`, veth pairs). Việc dùng `hostNetwork: true` để lách lỗi bind là anti-pattern nguy hiểm (gây xung đột port với Node và rò rỉ bảo mật).
- 2 điều còn thắc mắc:
  1. CNI Flannel sử dụng interface `flannel.1` để đóng gói VXLAN qua card `eth0` của Node như thế nào?
  2. Khi 2 Pod cùng node gọi nhau qua Pod IP, traffic có đi qua `flannel.1` không hay chỉ rẽ ngang qua bridge `cni0`? (Sẽ được bóc tách ở bài 14a).
- 1 thử nghiệm tiếp theo: Đo luồng gói tin giữa 2 Pod cùng Node (Same-node placement) ở bài [14a](lesson/14a-cni-va-same-node-placement.md).
