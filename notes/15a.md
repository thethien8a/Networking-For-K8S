## Mục tiêu

- Đo kiểm kết nối Pod-to-Pod cross-node (khác Node), bóc tách sự khác biệt L2/L3 so với baseline same-node ở bài 14b.

## Topology và địa chỉ IP

- **Node nguồn:** `k3d-de-k3d-agent-0` (Host IP: `192.168.155.4`, PodCIDR: `10.42.3.0/24`)
  - Pod Client: `client-cross-node` (IP: `10.42.3.22`)
  - Gateway: `cni0` (IP: `10.42.3.1`, MAC: `96:44:ea:17:28:57`)
  - Overlay Device: `flannel.1` (IP: `10.42.3.0/32`)
- **Node đích:** `k3d-de-k3d-agent-1` (Host IP: `192.168.155.3`, PodCIDR: `10.42.1.0/24`)
  - Pod Server: `server-cross-node` (IP: `10.42.1.19`, Listening: 8080/TCP)
  - Gateway: `cni0` (IP: `10.42.1.1`)
  - Overlay Device: `flannel.1` (IP: `10.42.1.0/32`)

### Data Path 2 chiều:
```
[ client-cross-node ] (10.42.3.22)
       │ (Default route qua 10.42.3.1)
   eth0 (Pod veth)
       │
[ k3d-de-k3d-agent-0 Host ]
   bridge cni0 (10.42.3.1, MAC 96:44:ea:17:28:57)
       │ (L3 Routing: 10.42.1.0/24 via 10.42.1.0 dev flannel.1 onlink)
   flannel.1 (VTEP)
       │ [Đóng gói VXLAN UDP 8472: Outer 192.168.155.4 -> 192.168.155.3]
   eth0 Host
       │
═══════╪═════════════════════════════════════════════════════════
       │ [ MẠNG UNDERLAY 192.168.155.0/24 ]
═══════╪═════════════════════════════════════════════════════════
       ▼
[ k3d-de-k3d-agent-1 Host ]
   eth0 Host
       │
   flannel.1 (VTEP)
       │ [Bóc vỏ VXLAN: Outer UDP dropped, lấy Inner IP 10.42.3.22 -> 10.42.1.19]
       │ (L3 Routing: 10.42.1.0/24 dev cni0)
   bridge cni0
       │
   eth0 (Pod veth)
       ▼
[ server-cross-node ] (10.42.1.19:8080)
```

## Các bước thực hành / câu lệnh

```bash
# 1. Tạo namespace nfk-15a và triển khai 2 Pod dùng nodeSelector
kubectl create namespace nfk-15a
kubectl apply -f manifest.yaml

# 2. Kiểm tra placement và IP
kubectl get pods -n nfk-15a -o wide

# 3. Đo kiểm HTTP và Ping cross-node
kubectl exec -n nfk-15a client-cross-node -- curl -s -I "http://10.42.1.19:8080" | head -n 1
kubectl exec -n nfk-15a client-cross-node -- ping -c 1 10.42.1.19

# 4. Kiểm tra ARP table bên trong client
kubectl exec -n nfk-15a client-cross-node -- ip neigh

# 5. Kiểm tra routing table trên Host agent-0
docker exec k3d-de-k3d-agent-0 ip route
```

## Bằng chứng

1. **Placement & Pod IP phân bố trên 2 worker khác nhau:**
```
NAME                READY   STATUS    RESTARTS   AGE   IP           NODE                 NOMINATED NODE   READINESS GATES
client-cross-node   1/1     Running   0          12s   10.42.3.22   k3d-de-k3d-agent-0   <none>           <none>
server-cross-node   1/1     Running   0          12s   10.42.1.19   k3d-de-k3d-agent-1   <none>           <none>
```
2. **HTTP và Ping thành công:**
```
HTTP/1.0 200 OK
64 bytes from 10.42.1.19: seq=0 ttl=42 time=0.151 ms
```
3. **So sánh độ trễ (Latency comparison):**
- Same-node (Module 14b): `0.054 ms`
- Cross-node (Module 15a): `0.151 ms` (chậm hơn ~3 lần do overhead đóng/mở gói VXLAN và chuyển tiếp mạng Underlay).
4. **Đối chứng bảng ARP `ip neigh` giữa same-node và cross-node:**
- Same-node: Client lưu trực tiếp MAC của Server Pod (`10.42.3.21 ... REACHABLE`).
- Cross-node: Client **chỉ lưu MAC của Default Gateway** `10.42.3.1` (bridge `cni0` MAC `96:44:ea:17:28:57`), không hề có MAC của Server Pod!
5. **Host routing table xác nhận điều hướng sang `flannel.1`:**
```
10.42.1.0/24 via 10.42.1.0 dev flannel.1 onlink
```

## Lỗi gặp phải và phân tích root cause

| Triệu chứng | Giả thuyết | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| Nhầm lẫn IP `10.42.3.1` trong `ip neigh` là IP của một Pod | Có thể tưởng là Pod khác | So sánh với `ip route` trong Pod (`default via 10.42.3.1`) và `ip addr show cni0` trên Host | `10.42.3.1` là IP của bridge `cni0` (Gateway của Pod), không phải của Pod |

## Cách sửa và bằng chứng xác minh

- Củng cố mental model: khi gói tin gửi ra ngoài subnet local `/24`, L3 kernel của Pod tra bảng routing và gửi tới Default Gateway (`10.42.3.1`). Do đó bảng ARP chỉ lưu MAC của Gateway.

## Rollback / dọn dẹp / tài nguyên còn giữ

- **Tài nguyên giữ lại:** Giữ namespace `nfk-15a` và 2 Pod `client-cross-node`, `server-cross-node` để làm baseline và phục vụ bài thực hành fault injection tiếp theo ở [15b — Bằng chứng và fault injection cho cross-node path](lesson/15b-cross-node-evidence-va-fault.md).

## Review và tự giải thích

- 3 điều hiểu được:
  1. Underlay là mạng nối các máy chủ vật lý; Overlay là mạng logic trừu tượng bọc gói tin Pod qua VXLAN.
  2. Giao tiếp cross-node bắt buộc qua Default Gateway `cni0`, định tuyến sang `flannel.1` để đóng gói UDP port 8472.
  3. Bảng ARP của Pod khi gọi cross-node chỉ học MAC của Gateway `cni0`, không học MAC của Server đích.
- 2 điều còn thắc mắc:
  1. Nếu cổng UDP 8472 trên mạng Underlay bị firewall chặn thì triệu chứng trên Client sẽ ra sao?
  2. Tại sao k3s/Flannel lại gán IP `dev flannel.1 onlink` cho cả dải subnet?
- 1 thử nghiệm tiếp theo: Tạo fault injection khoanh vùng lỗi cross-node ở bài 15b.
- Mức gợi ý cao nhất / có xem lời giải không: Tự làm / không cần gợi ý.
