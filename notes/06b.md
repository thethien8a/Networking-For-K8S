# 06b — Connect timeout, application timeout và retry

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-10-26 15:00 – 2026-10-26 16:05
- Thời lượng: 40 phút
- Máy thực thi / OS / cluster context / namespace: macOS Darwin host, Docker Engine (OrbStack), network cô lập `nfk-06b` (`10.250.62.0/24`). Học viên tự mở terminal chạy trực tiếp các lệnh kiểm tra kết nối curl và đo kiểm timeout giữa 2 container:
  - `nfk-06b-server` (`10.250.62.10`)
  - `nfk-06b-client` (`10.250.62.20`)
- Phiên bản và tài liệu đã đối chiếu: Alpine Linux 3.20/3.21, curl 8.23.0, python 3.12.15, iptables v1.8.13.

## Mục tiêu

- Chỉ ra chính xác giai đoạn kết nối bị kẹt (Bắt tay TCP Connect hay Đọc dữ liệu Application) thay vì quy chụp mù quáng vào "mạng chậm / rớt mạng".
- Phân biệt cơ chế và phạm vi tác động của 2 bộ đếm thời gian: `--connect-timeout` và `--max-time` (`-m`).
- Hiểu bản chất cơ chế Retry: Transient failure (503) mở socket mới có thể cứu request; Blackhole (DROP) hoặc server xử lý quá ngưỡng timeout thì Retry hoàn toàn vô ích và gây hại (Retry Storm, Duplicate Data).

## Các bước thực hành do học viên tự thực hiện

### 1. Phân biệt Connect Timeout vs Operation Timeout
Học viên chạy đo kiểm với `time curl -v`:
```bash
# Test 1: Cổng bị DROP
docker exec nfk-06b-client sh -c "time curl -v --connect-timeout 2 http://10.250.62.10:8001/"
# Kết quả: curl: (28) Connection timed out after 2006 milliseconds. real 0m 2.01s. Không có dòng Established connection.

# Test 2: Cổng HTTP xử lý chậm (/slow sleep 10s)
docker exec nfk-06b-client sh -c "time curl -v --connect-timeout 2 -m 3 http://10.250.62.10:8002/slow"
# Kết quả: Established connection to 10.250.62.10 port 8002. GET /slow Request completely sent off.
# curl: (28) Operation timed out after 3005 milliseconds with 0 bytes received. real 0m 3.01s.
```
Học viên nhận định chính xác: Test 1 kẹt ở giai đoạn kết nối (`Connection timed out`), Test 2 kết nối xong tức thì nên `--connect-timeout 2` hết hiệu lực, request chạy đến 3s thì bị cắt bởi `-m 3` (`Operation timed out`).

### 2. Thực chứng cơ chế Retry
Học viên chạy thử nghiệm 2 kịch bản retry:
```bash
# Kịch bản A: Lỗi tạm thời 503 (/flake)
docker exec nfk-06b-client curl -v --retry 3 --retry-delay 1 http://10.250.62.10:8002/flake
# Kết quả: Attempt 1 (port 36310) 503 -> Attempt 2 (port 36316) 503 -> Attempt 3 (port 36324) 200 OK SUCCESS ON ATTEMPT 3.

# Kịch bản B: Cổng bị DROP (8001)
docker exec nfk-06b-client curl -v --connect-timeout 2 --retry 2 --retry-delay 1 http://10.250.62.10:8001/
# Kết quả: Thử 3 lần (0, 1, 2), mỗi lần đợi 2s + delay 1s, tổng cộng ~8 giây vẫn thất bại dính curl: (28).
```
Học viên phân tích chuẩn xác:
- Kịch bản A: Mỗi lần retry là mở một kết nối TCP hoàn toàn mới (cổng ephemeral đổi liên tục).
- Kịch bản B: Gói tin đã bị DROP thì retry hoàn toàn vô dụng, chỉ làm tốn thời gian giam lỏng client.

### 3. Break & Fix: Triage case ẩn danh port 8003
- Bối cảnh: Pipeline ETL bị timeout 2 giây ở `http://10.250.62.10:8003/api/data`. Kỹ sư nghi ngờ rớt mạng/firewall và đòi bật retry 5 lần.
- Học viên đo kiểm với lệnh:
  ```bash
  docker exec nfk-06b-client curl -v --connect-timeout 2 -m 2 http://10.250.62.10:8003/api/data
  ```
- Kết quả đo: `Operation timed out`, dòng `* Established connection to 10.250.62.10 port 8003` xuất hiện rõ ràng.
- Kết luận của học viên:
  - Bác bỏ hoàn toàn nghi vấn mạng rớt hay firewall. Mạng và port thông suốt 100%.
  - Retry 5 lần với timeout 2s vô tác dụng vì backend cần nhiều hơn 2s để xử lý.
  - Sửa đúng bản chất: Tăng timeout lên `-m 10` (hoặc tối ưu backend).
- Kiểm chứng thực tế: Chạy `-m 10` thành công nhận về JSON `{"status": "success", "data": [1, 2, 3]}` sau ~6 giây.

## Review và tự giải thích

- 3 điều hiểu được:
  1. Phân biệt rạch ròi giữa Connect Timeout (bắt tay TCP thất bại do DROP/đứt mạng) và Application/Read Timeout (TCP xong, server app xử lý chậm).
  2. Cờ `--connect-timeout` chỉ đếm lúc handshake; khi đã kết nối thì `--max-time` (`-m`) là chiếc đồng hồ quyết định.
  3. Retry chỉ hiệu quả với lỗi tạm thời (transient 503/429) và request idempotent; vô dụng với lỗi mạng triệt để (DROP) và nguy hiểm nếu áp dụng bừa bãi cho request ghi dữ liệu.
- 2 điều còn thắc mắc: (Không có thắc mắc còn tồn đọng).
- 1 thử nghiệm tiếp theo: Khảo sát tầng DNS ở bài 07a.
- Câu áp dụng sang tình huống khác: Phân biệt timeout giữa Spark Driver và PostgreSQL qua việc soi kỹ thông điệp lỗi trong log (`Connection timed out` vs `SocketTimeoutException / Read timed out`) và kiểm tra `pg_stat_activity` trên database.
