## Topology và địa chỉ IP

```
[ Máy Host của học viên (Client) ]
       │ (Gọi tới: 127.0.0.1:8888)
       ▼
[ Docker Port Mapping / NAT ]
       │ (DNAT sang: 10.250.85.10:80, SNAT sang: 10.250.85.1)
       ▼
[ Backend Container: nfk-08b-backend (10.250.85.10:80) ]
       ▲
       │ (Gọi nội bộ trực tiếp: Source 10.250.85.20 -> Dest 10.250.85.10:80)
[ Client Container: nfk-08b-client (10.250.85.20) ]
```

## Các bước thực hành / câu lệnh

1. Học viên chạy lệnh từ Host terminal để đo kiểm Port Mapping qua NAT:
   ```bash
   curl -v http://127.0.0.1:8888/
   ```
2. Học viên chạy lệnh từ container nội bộ để đo kiểm đối chứng không qua NAT:
   ```bash
   docker exec nfk-08b-client curl -s http://10.250.85.10:80/
   ```
3. Phép đo chẩn đoán Break & Fix:
   - Gọi port chưa map `curl -v http://127.0.0.1:8889/`
   - Đo kiểm tra container crash / port đóng với dummy mapped container
   - Kiểm tra L7 Host mismatch

## Bằng chứng

- **Bằng chứng 1 (Bảng 4-tuple qua Port Mapping có DNAT và SNAT):**
  ```text
  * Trying 127.0.0.1:8888...
  * Connected to 127.0.0.1 (127.0.0.1) port 8888
  > GET / HTTP/1.1
  > Host: 127.0.0.1:8888
  < HTTP/1.0 200 OK
  === BACKEND RECEIVED REQUEST ===
  Destination (IP:Port) seen by Backend: 10.250.85.10:80
  Source (IP:Port) seen by Backend:      10.250.85.1:41067
  Host Header received:                  127.0.0.1:8888
  ```
  *Phân tích:* Destination chuyển từ `127.0.0.1:8888` $\to$ `10.250.85.10:80` (DNAT). Source chuyển từ client $\to$ `10.250.85.1` (SNAT/Masquerade). L7 Host Header giữ nguyên không đổi.

- **Bằng chứng 2 (Giao tiếp nội bộ cùng subnet bảo toàn Source IP):**
  ```text
  === BACKEND RECEIVED REQUEST ===
  Destination (IP:Port) seen by Backend: 10.250.85.10:80
  Source (IP:Port) seen by Backend:      10.250.85.20:56060
  Host Header received:                  10.250.85.10
  ```
  *Phân tích:* Source IP `10.250.85.20` được giữ nguyên vẹn 100%, không bị rewrite qua NAT.

- **Bằng chứng 3 (Phân biệt 3 kịch bản sự cố Break & Fix):**
  - *Sai Mapped Port (8889):* `curl: (7) Failed to connect to 127.0.0.1 port 8889: Connection refused` (TCP Handshake thất bại ngay tại Host).
  - *Backend crash / không listen:* Host bắt tay TCP thành công (`Connected`), nhưng sau đó bị ngắt `curl: (56) Recv failure: Connection reset by peer` do port đích trong container từ chối.
  - *L7 Virtual Host mismatch:* TCP và TLS đều thành công, nhưng nhận mã lỗi HTTP L7 `400/404/421`.

## Đánh giá Cổng Checkpoint 2 (CP2)

- **Tiêu chí 1: Phân loại 4 tầng lỗi (DNS, TCP, TLS, HTTP):** Đạt.
  - (a) `Could not resolve host` -> DNS.
  - (b) `Failed to connect ... Connection refused` -> TCP.
  - (c) `SSL certificate problem: unable to get local issuer certificate` -> TLS.
  - (d) `HTTP/1.1 503 Service Unavailable` -> HTTP.
- **Tiêu chí 2: Phân biệt Connect Timeout vs Application Timeout, Refused vs Drop:** Đạt.
  - Connect Timeout: Chưa hoàn thành 3-way handshake (gói SYN bị DROP mất tích dọc đường).
  - Application Timeout: Đã hoàn thành 3-way handshake (ESTABLISHED), ứng dụng xử lý chậm không trả data.
  - `Connection refused` (RST): Bằng chứng thép chứng minh gói tin đã tới được OS máy chủ đích và máy chủ còn sống (phản hồi RST do đóng port). Ngược lại, `Connection timed out` (DROP) xảy ra do mất gói dọc đường hoặc firewall DROP, không chứng minh được tới máy chủ.
- **Tiêu chí 3: Bóc tách vai trò của Hostname:** Đạt.
  - Dùng ở 3 mốc: DNS lookup, TLS SNI (chọn và verify cert), và HTTP `Host` header.
  - Khi cert không khớp domain URL, gãy ở bước xác thực chứng chỉ TLS (`no alternative certificate subject name matches`); header `-H "Host: ..."` vô dụng vì nằm trong đường hầm mã hóa L7 chưa được mở.
- **Tiêu chí 4: Bản chất của NAT:** Đạt.
  - SNAT đổi IP nguồn; DNAT đổi IP đích.
  - NAT chỉ là cơ chế rewrite địa chỉ IP/port, không phải là firewall (không lọc gói stateful, không thể thay thế NetworkPolicy/Iptables filter).

## Review và tự giải thích

- 3 điều hiểu được:
  1. DNAT thay đổi Destination IP:Port (dùng cho Port Mapping, Kubernetes NodePort/Service), SNAT thay đổi Source IP:Port (dùng khi ra ngoài qua Gateway).
  2. Pod-to-Pod trong Kubernetes (cũng như container cùng Docker bridge) giao tiếp không bị NAT, bảo toàn Source IP gốc.
  3. Phân biệt được sự khác nhau giữa `Connection refused` (đã tới host nhưng port đóng), `Connection reset by peer` (backend chết sau khi proxy kết nối), và L7 HTTP errors.
- 2 điều còn thắc mắc:
  1. Trong Kubernetes, kube-proxy dùng iptables hay IPVS để thực hiện DNAT từ Service ClusterIP sang Pod IP như thế nào?
  2. Khi Pod gọi ra ngoài Internet, CNI thực hiện SNAT/Masquerade tại node ra sao?
- 1 thử nghiệm tiếp theo: Khảo sát Linux network inventory và network namespace ở bài 09a.
- Câu áp dụng sang tình huống khác và câu trả lời:
  - Khi Ingress Controller nhận traffic từ bên ngoài, làm sao backend Pod nhìn thấy được IP thật của người dùng (Real Client IP) nếu gói tin bị SNAT?
  - Trả lời: Sử dụng HTTP header `X-Forwarded-For` hoặc `X-Real-IP`, hoặc bật PROXY protocol ở Layer 4.
- Mức gợi ý cao nhất / có xem lời giải không: Tự làm / không gợi ý (giải thích đúng toàn bộ cơ chế).
