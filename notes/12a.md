# 12a — Packet filtering, hooks và connection tracking

- Phiên bản và tài liệu đã đối chiếu: Linux iptables 1.8.13, conntrack-tools 1.4.9, Linux Netfilter architecture documentation.
- Phạm vi được phép thay đổi: Container lab riêng `nfk-12a-lab` và 3 network namespaces (`ns-a`, `ns-b`, `ns-router`). Tuyệt đối không chạm tới background cluster `k3d-de-k3d-*` hay network của host.

## Mục tiêu

- Phân biệt ba ngã rẽ lưu lượng của Netfilter hooks: `INPUT` (Local delivery), `FORWARD` (Transit traffic), `OUTPUT` (Local generated).
- Kiểm chứng thực nghiệm sự khác biệt bản chất giữa Socket tầng ứng dụng (`ss -t`) và Connection Tracking tầng kernel (`conntrack -L`).
- Nắm vững nguyên lý hoạt động của Stateful Firewall (`ctstate NEW` vs `ctstate ESTABLISHED,RELATED`).

## Dự đoán trước lab

| Phép thử | Kết quả dự đoán | Vì sao / giả định |
|---|---|---|
| Chặn ICMP ở chain `INPUT` trên Router | Ping Router bị chặn (100% loss), nhưng ping xuyên Router sang B vẫn thành công (0% loss) | Sau Routing Decision, gói gửi cho chính Router mới rẽ vào `INPUT`. Gói gửi sang B rẽ vào `FORWARD`, hoàn toàn không đi qua `INPUT`. |
| Chặn `ctstate NEW -j DROP` trên Router | Kết nối mới bị timeout, kết nối cũ `ESTABLISHED` không bị ảnh hưởng | Kernel lưu trạng thái flow trong conntrack; rule chỉ bắt gói SYN mở kết nối mới (`NEW`), các gói thuộc flow cũ được thông qua. |

## Topology và 3 Ngã Rẽ Netfilter

```
[ ns-a ] 10.100.1.2/24 (Client)
   │
   │ (veth-a -> veth-ra)
   ▼
[ ns-router ]
   │
   ├─► [ Routing Decision: IP đích == 10.100.1.1? ] ──► [ INPUT Hook ] (Local Delivery)
   │                                                         │
   │                                                         ▼ (iptables -A INPUT -p icmp -j DROP)
   │                                                    [ DROP: 2 pkts ]
   │
   └─► [ Routing Decision: IP đích == 10.100.2.2? ] ──► [ FORWARD Hook ] (Transit Traffic)
                                                             │
                                                             ├─► ctstate RELATED,ESTABLISHED ──► ACCEPT
                                                             └─► ctstate NEW ──► DROP
                                                             │
                                                             ▼ (veth-rb -> veth-b)
                                                   [ ns-b ] 10.100.2.2:8080 (Server)
```

## Các bước thực hành và kết quả đo kiểm

1. **Khởi tạo topology A ↔ Router ↔ B:**
   - 3 namespaces: `ns-a`, `ns-b`, `ns-router`.
   - 2 dải subnet riêng: `10.100.1.0/24` và `10.100.2.0/24`.
   - Bật `net.ipv4.ip_forward = 1` trên `ns-router`.
2. **Thực nghiệm ngã rẽ `INPUT` vs `FORWARD`:**
   - Đặt rule chặn trên Router: `iptables -A INPUT -p icmp -j DROP`.
   - Phép đo 1: `ns-a ping 10.100.1.1` (Router) -> `100% packet loss` (bị drop tại INPUT).
   - Phép đo 2: `ns-a ping 10.100.2.2` (Server B) -> `0% packet loss`, RTT ~0.09ms, `ttl=63` (thoát qua FORWARD bình thường).
   - Kiểm tra counter: `iptables -L INPUT -v -n` ghi nhận chính xác `2 pkts 168 bytes DROP`.
   - Hoàn nguyên: Xóa rule DROP trên INPUT.
3. **Thực nghiệm Socket vs Conntrack:**
   - Chạy HTTP server port 8080 ở `ns-b`.
   - Nạp rule: `iptables -A FORWARD -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT` (đánh thức conntrack trong namespace).
   - Client A curl HTTP sang Server B -> `HTTP/1.0 200 OK`.
   - So sánh tại Router:
     - `ss -t`: Trống rỗng (Router không tốn socket nào vì không sở hữu application process).
     - `conntrack -L`: Ghi nhận flow 2 chiều đầy đủ:
       `tcp 6 104 TIME_WAIT src=10.100.1.2 dst=10.100.2.2 sport=40278 dport=8080 src=10.100.2.2 dst=10.100.1.2 sport=8080 dport=40278 [ASSURED]`
4. **Thực nghiệm Stateful Firewall (`ctstate NEW`):**
   - Thêm rule: `iptables -A FORWARD -m conntrack --ctstate NEW -j DROP`.
   - Client A mở kết nối mới: `curl --connect-timeout 2` -> Bị timeout!
   - Kiểm tra counter: `iptables -L FORWARD -v -n` ghi nhận đúng `2 pkts 120 bytes DROP ctstate NEW`.
   - Hoàn nguyên: Xóa rule DROP NEW, curl phục hồi `HTTP/1.0 200 OK`.

## Lỗi gặp phải và phân tích root cause

| Triệu chứng | Giả thuyết | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| `conntrack -L` ban đầu trống rỗng dù đã curl | Linux kernel tối ưu tài nguyên, không bật hook conntrack trong netns nếu chưa có rule yêu cầu | Thêm rule có `-m conntrack` rồi curl lại | Sau khi thêm rule `-m conntrack`, flow entry xuất hiện ngay lập tức trong bảng conntrack. |

## Rollback / dọn dẹp / tài nguyên còn giữ

- Toàn bộ các rule iptables thử nghiệm (`DROP` trên INPUT, `DROP NEW` trên FORWARD) đã được xóa bỏ sạch sẽ.
- Giữ container `nfk-12a-lab` với HTTP baseline sạch cho bài tiếp theo [12b — DROP, REJECT, rollback và Checkpoint 3](../lesson/12b-drop-reject-va-cp3.md) theo đúng yêu cầu giáo trình.

## Review và tự giải thích

- 3 điều hiểu được:
  1. Gói tin đi vào máy được phân luồng tại Routing Decision: IP của chính máy đi vào `INPUT`, IP của máy khác đi vào `FORWARD`. Chặn `INPUT` không ảnh hưởng tới `FORWARD`.
  2. Router L3 chuyển tiếp hàng triệu kết nối mà không tốn socket (`ss -t` rỗng), nhưng kernel của Router lưu flow trong bảng `conntrack` (`[ASSURED]`).
  3. Stateful Firewall cho phép phân biệt gói mở kết nối (`NEW`) với gói thuộc kết nối đã thông qua (`ESTABLISHED`), là nền tảng của Kubernetes NetworkPolicy.
- 2 điều còn thắc mắc:
  1. Khi firewall dùng `DROP` thì client bị timeout, vậy khi dùng `REJECT` thì client nhận được gì ngay lập tức?
  2. Bảng conntrack có kích thước tối đa là bao nhiêu và khi bị tràn thì triệu chứng trên Kubernetes node là gì?
- 1 thử nghiệm tiếp theo: So sánh chi tiết cơ chế DROP vs REJECT và vượt Cổng đánh giá Checkpoint 3 trong bài 12b.
- Câu áp dụng sang tình huống khác:
  - Tình huống: Spark job với hàng ngàn executor mở kết nối liên tục, node báo `nf_conntrack: table full, dropping packet`.
  - Phân tích: Bảng conntrack bị tràn do connection churn quá cao. Xử lý bằng cách tăng `net.netfilter.nf_conntrack_max`, giảm timeout close/time_wait hoặc dùng connection pool.
- Mức gợi ý cao nhất / có xem lời giải không: Tự làm độc lập theo hướng dẫn Mental Model của LLM.
