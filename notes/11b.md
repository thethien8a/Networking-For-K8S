# 11b — Return path, forwarding và lỗi một chiều

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-11-03 23:25
- Thời lượng: 40 phút
- Máy thực thi / OS / cluster context / namespace: macOS Darwin arm64 (Apple Silicon), Docker runtime (OrbStack), container `nfk-11a-lab` (image `nfk-07b-tools:local`) với `--cap-add NET_ADMIN --cap-add SYS_ADMIN`.
- Phiên bản và tài liệu đã đối chiếu: Linux iproute2 (`ip route get`), sysctl `net.ipv4.ip_forward`, RFC 791 / RFC 1812.
- Phạm vi được phép thay đổi: Container lab riêng `nfk-11a-lab` và 3 network namespaces (`ns-a`, `ns-b`, `ns-router`). Tuyệt đối không chạm tới background cluster `k3d-de-k3d-*` hay network của host.

## Mục tiêu

- Phân biệt sự khác biệt về mặt bản chất giữa lỗi **Router tắt forwarding** (`ip_forward=0`) và **Server thiếu route trả về** (missing return path).
- Nắm vững Mental Model điều tra mạng hai chiều: dùng lệnh `ip route get <IP>` để tra cứu quyết định định tuyến của kernel và `sysctl net.ipv4.ip_forward` để kiểm tra van chuyển tiếp.
- Hiểu tính chất định tuyến độc lập ở từng hop và từng chiều của luồng TCP/HTTP.

## Dự đoán trước lab

| Phép thử | Kết quả dự đoán | Vì sao / giả định |
|---|---|---|
| Router tắt forwarding (`ip_forward=0`) | Gói SYN đến `veth-ra`, mất ở `veth-rb` | Router nhận gói tin transit nhưng van forward đóng nên kernel drop gói tin ngay tại Router, không đẩy sang card giáp B. |
| Server B thiếu route về A | Gói SYN đi qua cả 2 card của Router tới B, nhưng không có gói SYN-ACK nào xuất hiện | B nhận được SYN, nhưng khi muốn trả lời SYN-ACK thì B không có route về A. Gói SYN-ACK bị drop ngay trong kernel của B. |
| Ping tới Router thành công có chứng minh Router đang forward tốt sang B? | Không | Ping Router là Local Delivery (INPUT chain). Gói sang B là Transit Forwarding (FORWARD chain). |

## Topology và luồng dữ liệu hai chiều (Request & Response)

```
[ Request Path: A -> B ]
Client A (10.100.1.2)
  └─ [Route Table A: default via 10.100.1.1 dev veth-a]
        │ (veth-a -> veth-ra)
        ▼
Router (10.100.1.1 / 10.100.2.1)
  └─ [Cần net.ipv4.ip_forward = 1]
  └─ [Route Table Router: 10.100.2.0/24 dev veth-rb]
        │ (veth-rb -> veth-b)
        ▼
Server B (10.100.2.2:8080)

-----------------------------------------------------------

[ Response Path: B -> A ]
Server B (10.100.2.2)
  └─ [Route Table B: default via 10.100.2.1 dev veth-b] (BẮT BUỘC PHẢI CÓ!)
        │ (veth-b -> veth-rb)
        ▼
Router (10.100.2.1 / 10.100.1.1)
  └─ [Cần net.ipv4.ip_forward = 1]
  └─ [Route Table Router: 10.100.1.0/24 dev veth-ra]
        │ (veth-ra -> veth-a)
        ▼
Client A (10.100.1.2)
```

## Các bước thực hành và điều tra hai sự cố

### 1. Sự cố #1 (Ẩn nguyên nhân: Server B mất route chiều về)
- **Triệu chứng:** Đứng tại `ns-a`, lệnh `curl -s -I --connect-timeout 2 http://10.100.2.2:8080/` bị timeout.
- **Áp dụng Mental Model đo kiểm:**
  1. Hỏi Router: `docker exec nfk-11a-lab ip netns exec ns-router sysctl net.ipv4.ip_forward`
     -> Kết quả: `net.ipv4.ip_forward = 1` (Router vô tội).
  2. Hỏi Server B: `docker exec nfk-11a-lab ip netns exec ns-b ip route get 10.100.1.2`
     -> Kết quả: `RTNETLINK answers: Network unreachable` (Bắt quả tang: Server B thiếu route về A).
- **Khắc phục:** Thêm default route trên B:
  `docker exec nfk-11a-lab ip netns exec ns-b ip route add default via 10.100.2.1`
- **Nghiệm thu:** 
  - `ip route get 10.100.1.2` -> `10.100.1.2 via 10.100.2.1 dev veth-b src 10.100.2.2`.
  - `curl` từ `ns-a` phục hồi: `HTTP/1.0 200 OK`.

### 2. Sự cố #2 (Ẩn nguyên nhân: Router bị tắt IP Forwarding)
- **Triệu chứng:** Đứng tại `ns-a`, `curl` sang `ns-b` tiếp tục bị timeout.
- **Áp dụng Mental Model đo kiểm:**
  1. Hỏi Server B: `docker exec nfk-11a-lab ip netns exec ns-b ip route get 10.100.1.2`
     -> Kết quả: `10.100.1.2 via 10.100.2.1 dev veth-b` (Server B vô tội, route về vẫn còn nguyên).
  2. Hỏi Router: `docker exec nfk-11a-lab ip netns exec ns-router sysctl net.ipv4.ip_forward`
     -> Kết quả: `net.ipv4.ip_forward = 0` (Bắt quả tang: Router đóng van chuyển tiếp).
- **Khắc phục:** Bật lại IP Forwarding trên Router:
  `docker exec nfk-11a-lab ip netns exec ns-router sysctl -w net.ipv4.ip_forward=1`
- **Nghiệm thu:**
  - `curl` từ `ns-a` phục hồi: `HTTP/1.0 200 OK`.

## Lỗi gặp phải và phân tích root cause

| Triệu chứng | Giả thuyết | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| Client curl timeout ở Case 1 | Server B không có route trả lời về A | Chạy `ip route get 10.100.1.2` trong `ns-b` | Báo `RTNETLINK answers: Network unreachable`. Kernel của B drop gói SYN-ACK tại nguồn. |
| Client curl timeout ở Case 2 | Router bị tắt IP Forwarding | Chạy `sysctl net.ipv4.ip_forward` trong `ns-router` | Giá trị là `0`. Router drop gói transit ngay tại FORWARD chain. |

## Review và tự giải thích

- 3 điều hiểu được:
  1. Triệu chứng bên ngoài giống nhau (Client timeout) có thể do nhiều nguyên nhân khác nhau ở các tầng trung gian hoặc phía đối tác trả lời.
  2. Lệnh `ip route get <IP>` là công cụ chẩn đoán định tuyến nhanh và chính xác nhất trên Linux để kiểm tra kernel sẽ định tuyến một IP cụ thể ra sao.
  3. Tư duy bóc tách sự cố quan trọng hơn việc thuộc lòng cú pháp lệnh. Biết đặt câu hỏi cho Router (`ip_forward`) và Server (`ip route get`) giúp cô lập lỗi trong vài giây.
- 2 điều còn thắc mắc:
  1. Khi hệ thống có nhiều router (dynamic routing BGP / OSPF như trong mạng Calico), nếu đường đi và đường về qua 2 router khác nhau (asymmetric routing) thì có gây lỗi kết nối không?
  2. Khi có iptables / firewall Stateful (conntrack), việc định tuyến bất đối xứng bị ảnh hưởng thế nào?
- 1 thử nghiệm tiếp theo: Tìm hiểu firewall Linux và conntrack trong Module 12.
- Câu áp dụng sang tình huống khác:
  - Tình huống: Pod Kafka nhận message từ Producer khác node. Producer bị timeout chờ ACK. Logs của Kafka pod xác nhận đã nhận được message.
  - Kết luận: Chiều đi từ Producer sang Kafka thành công 100%. Sự cố chắc chắn nằm ở chiều về (Return path từ Kafka về Producer hoặc router/firewall chặn gói ACK).
- Mức gợi ý cao nhất / có xem lời giải không: Tự phân tích dựa trên câu lệnh đo lường được LLM cung cấp theo Mental Model; không cần xem lời giải.
