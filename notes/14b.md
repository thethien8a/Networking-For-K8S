# 14b — Quan sát Pod-to-Pod data path cùng node

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-11-06 10:25
- Thời lượng: 35 phút
- Máy thực thi / OS / cluster context / namespace: macOS Darwin arm64 / k3d-de-k3d / namespace `nfk-14a`
- Phiên bản và tài liệu đã đối chiếu: K3s v1.33.6+k3s1, Flannel CNI (bridge plugin + vxlan backend)
- Phạm vi được phép thay đổi: Namespace `nfk-14a`

## Mục tiêu

- Vẽ đường đi gói tin (Data Path) thực tế giữa hai Pod cùng Node; phân biệt quan sát thực tế trên kernel với phỏng đoán.
- Phân biệt rạch ròi lỗi tầng mạng L2/L3 (CNI, veth, bridge) với lỗi tầng ứng dụng L4 (Listener, port mismatch).

## Dự đoán trước lab

| Phép thử | Kết quả dự đoán | Vì sao / giả định |
|---|---|---|
| Traffic cùng node có đi qua interface tunnel `flannel.1` không? | Không | Hai Pod cùng subnet Node PodCIDR (`10.42.3.0/24`), chuyển mạch L2 qua bridge `cni0`. |
| Server đổi sang port 9999 thì Client gọi 8080 bị gì? | Connection refused | TCP RST từ kernel của server vì socket 8080 không tồn tại; CNI và L2/L3 vẫn hoạt động. |
| Vị trí Node và Pod IP có bị đổi khi đổi port không? | Không | Port là thuộc tính L4 của socket tiến trình, không ảnh hưởng L3 IP và Scheduler placement. |

## Topology và địa chỉ IP

```
[client-same-node] (10.42.3.20)
      eth0 (if2, MAC de:59:... / new: de:...)
        │
    (veth pair)
        │
[k3d-de-k3d-agent-0 Host]
      veth... (master cni0 state UP)
        │
      └───> [ cni0 (Linux Bridge L2 Switching) ] <───┐
                                                     │
      veth... (master cni0 state UP) <───────────────┘
        │
    (veth pair)
        │
[server-same-node] (10.42.3.21)
      eth0 (if2, MAC 1e:6e:55:6c:91:03)
      Listening: 0.0.0.0:9999
```

- Không đi qua interface `flannel.1` (VXLAN).
- Không đi qua gateway `10.42.3.1` (giao tiếp link-local L2).

## Các bước thực hành / câu lệnh

```bash
# 1. Bóc tách L2/L3 trong client
kubectl exec -n nfk-14a client-same-node -- ip route
kubectl exec -n nfk-14a client-same-node -- ip neigh

# 2. Kiểm tra MAC eth0 của server
kubectl exec -n nfk-14a server-same-node -- ip link show eth0

# 3. Quan sát các cổng cắm vào bridge cni0 trên Node
docker exec k3d-de-k3d-agent-0 ip link show master cni0

# 4. Break & Fix: Gọi port cũ 8080 (khiến kết nối thất bại)
kubectl exec -n nfk-14a client-same-node -- curl -v --connect-timeout 2 "http://10.42.3.21:8080"

# 5. Đo kiểm L2/L3 đối chứng
kubectl exec -n nfk-14a client-same-node -- ping -c 1 10.42.3.21
kubectl exec -n nfk-14a client-same-node -- ip neigh

# 6. Sửa đúng L4: Gọi port 9999
kubectl exec -n nfk-14a client-same-node -- curl -s -I "http://10.42.3.21:9999" | head -n 1
```

## Bằng chứng

1. **Routing link-local:**
```
10.42.3.0/24 dev eth0 scope link src 10.42.3.20
```
2. **Neighbor cache L2 (ARP resolved):**
```
10.42.3.21 dev eth0 lladdr 1e:6e:55:6c:91:03 ref 1 used 0/0/0 probes 4 REACHABLE
```
3. **Bridge cni0 trên Node nhận các đầu veth:**
```
5: veth0bb804aa@if2: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1450 qdisc noqueue master cni0 state UP
6: veth51b054f0@if2: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1450 qdisc noqueue master cni0 state UP
7: veth43dbf233@if2: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1450 qdisc noqueue master cni0 state UP
```
4. **Đối chứng Break & Fix:**
- Port 8080: `* connect to 10.42.3.21 port 8080 failed: Connection refused after 0 ms`
- Ping L3: `64 bytes from 10.42.3.21: seq=0 ttl=42 time=0.054 ms`, `0% packet loss`
- Port 9999 (Fixed): `HTTP/1.0 200 OK`

## Lỗi gặp phải và phân tích root cause

| Triệu chứng | Giả thuyết | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| `docker exec k3d-de-k3d-agent-0 ip link show master cni0` báo `Device does not exist` | Node vừa reboot, kubelet agent bị ngắt kết nối tạm thời; bridge cni0 chỉ được tạo on-demand khi có Pod đầu tiên chạy | `kubectl get nodes` thấy NotReady, restart container agent | Sau khi agent Ready và Pod chạy, cni0 lập tức xuất hiện |
| `curl: (7) Failed to connect after 0 ms: Connection refused` | Nghi vấn CNI hỏng hoặc veth tuột vs L4 port mismatch | Chạy ping và ip neigh | Ping 0% loss 0.054ms, ARP REACHABLE -> L2/L3 khỏe, lỗi L4 port mismatch |

## Cách sửa và bằng chứng xác minh

- Gọi đúng cổng ứng dụng đang mở (`http://${SERVER_IP}:9999`). Kết quả trả về `HTTP/1.0 200 OK` ngay lập tức mà không cần can thiệp hạ tầng mạng.

## Review và tự giải thích

- 3 điều hiểu được:
  1. Giao tiếp Pod-to-Pod cùng Node diễn ra ở Layer 2 thông qua Linux Bridge (`cni0`), không đi qua overlay tunnel (`flannel.1`).
  2. Interface `cni0` được CNI plugin khởi tạo động (on-demand); nếu Node chưa Ready và chưa có Pod thì `cni0` chưa tồn tại.
  3. `Connection refused` (0ms) đi kèm `ping 0% loss` là bằng chứng thép chứng minh CNI và L2/L3 hoàn hảo, lỗi thuần túy là L4 application listener/port.
- 2 điều còn thắc mắc:
  1. Khi 2 Pod nằm ở 2 Node khác nhau thì gói tin sẽ đi qua `flannel.1` như thế nào?
  2. Overlay network đóng gói gói tin ra sao để đi qua mạng vật lý (Underlay)?
- 1 thử nghiệm tiếp theo: Bắt gói tin cross-node và khảo sát VXLAN encapsulation ở Module 15a.
- Mức gợi ý cao nhất / có xem lời giải không: Tự làm / không cần gợi ý.
