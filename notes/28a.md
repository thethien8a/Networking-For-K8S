## 4. Phân tích Luồng Dữ Liệu Hai Chiều (Data Paths)

### 4.1. Pod ↔ Pod cùng Node (Same-node)
- **Path:** `Pod A veth` → `cni0 bridge` → `Pod B veth`.
- **Cơ chế:** L2 switching thuần túy bên trong Linux bridge `cni0` của kernel.
- **Header:** Giữ nguyên IP gốc của Pod, MAC đích là MAC của Pod B học qua ARP. Hoàn toàn không đóng gói VXLAN, không đi qua `flannel.1` hay card vật lý `eth0`.
- **Bằng chứng kiểm chứng:** Đã kiểm chứng thực tế tại bài [14b](notes/14b.md).

### 4.2. Pod ↔ Pod khác Node (Cross-node Overlay)
- **Path:** `Pod A veth` → `cni0 bridge` → `flannel.1` (Linux VXLAN netdevice) → Encapsulation UDP 8472 (Outer header: Source Node IP, Dest Node IP, VNI=1) → `eth0` → VMware vSwitch → `eth0` Node B → `flannel.1` (Decapsulation) → `cni0` → `Pod B veth`.
- **Header:** Outer IP là Underlay IP (`192.168.10.x`), Inner IP là Pod IP (`10.244.x.x`).
- **MTU & Overhead:** Gói tin bị đội thêm **50 bytes header** (14 bytes Ethernet + 20 bytes Outer IP + 8 bytes UDP + 8 bytes VXLAN).
  - *Nếu Underlay MTU = 1500:* Pod MTU bắt buộc phải cấu hình giảm xuống **1450 bytes** (`1500 - 50 = 1450`) để tránh hiện tượng phân mảnh (fragmentation) hoặc rơi gói Silent DROP khi có cờ DF (Don't Fragment) như đã bóc tách ở bài [25b](notes/25b.md).
  - *Khuyến nghị hạ tầng:* Yêu cầu team VMware cấu hình **Jumbo Frames (MTU >= 1600)** trên vSwitch và Switch vật lý.
- **Bằng chứng kiểm chứng:** Đã kiểm chứng thực tế tại bài [15a](notes/15a.md), [15b](notes/15b.md), [16b](notes/16b.md), [25b](notes/25b.md).

### 4.3. Pod ↔ Service (ClusterIP)
- **Path:** `Pod veth` → `cni0` → Host Netfilter PREROUTING / OUTPUT chain.
- **Cơ chế:** Kube-proxy iptables bắt gói qua chuỗi `KUBE-SERVICES` → `KUBE-SVC-*` → chọn ngẫu nhiên `KUBE-SEP-*` bằng module `statistic --mode random` → thực hiện **DNAT** đổi ClusterIP đích thành Pod IP backend đích.
- **Return Path:** Conntrack ghi nhớ phiên NAT, tự động thực hiện **Un-DNAT** đổi Pod IP nguồn thành ClusterIP khi gửi trả về cho Client.
- **Bằng chứng kiểm chứng:** Đã kiểm chứng thực tế tại bài [17a](notes/17a.md), [18a](notes/18a.md), [18b](notes/18b.md).

### 4.4. Pod → External Egress (Truy cập Internet / Mạng công ty)
- **Path:** `Pod veth` → `cni0` → Host Netfilter POSTROUTING chain → Khớp rule `FLANNEL-POSTRTG` → Thực hiện **MASQUERADE (SNAT)** đổi Source IP từ Pod IP (`10.244.x.x`) thành IP card mạng vật lý của Node (`192.168.10.x`) → Gateway `192.168.10.1` → External Server.
- **Return Path:** External Server trả lời về Node IP. Conntrack trên Node un-SNAT và đưa ngược lại qua `cni0` về Pod.
- **Bằng chứng kiểm chứng:** Đã kiểm chứng thực tế tại bài [25a](notes/25a.md).

### 4.5. External Client → LoadBalancer (MetalLB L2) → Ingress / Service → Pod
- **Path:** Client ngoài → Gửi ARP tìm MAC của VIP `192.168.10.240` → Leader Node (được MetalLB bầu) trả lời ARP Reply chứa MAC của card `eth0` mình → Client gửi frame L2 tới Node Leader → Kube-proxy xử lý DNAT tới Pod backend (có thể nằm ở Node khác qua VXLAN).
- **Yêu cầu hạ tầng VMware sống còn:** vSwitch Port Group **bắt buộc phải cấu hình `MAC Address Changes: Accept` và `Forged Transmits: Accept`**. Nếu để mặc định `Reject`, vSwitch của VMware sẽ chặn đứng gói tin ARP của MetalLB, khiến client ngoài không học được MAC và bị Timeout!
- **Bằng chứng kiểm chứng:** Đã kiểm chứng mô phỏng thực tế tại bài [23b](notes/23b.md).

## 5. DNS, Thời Gian (NTP) và Dependency

1. **Pod Resolver & `ndots:5`:**
   - Pod thừa hưởng file `/etc/resolv.conf` do Kubelet inject: `nameserver 10.96.0.10`, `search <ns>.svc.cluster.local svc.cluster.local cluster.local`, `options ndots:5`.
   - *Rủi ro Data Engineering:* Các query tên miền ngoài (như S3 endpoint, Kafka cluster FQDN) nếu có ít hơn 5 dấu chấm sẽ bị libc search nối đuôi 3 lần trong cụm K8s gây lãng phí băng thông CoreDNS và tăng độ trễ 20-30ms như đã mổ xẻ ở bài [19a](notes/19a.md).
   - *Giải pháp:* Cấu hình FQDN tuyệt đối có dấu chấm đuôi (trailing dot: `s3.ap-southeast-1.amazonaws.com.`) trong cấu hình ứng dụng Spark/Airflow.
2. **NTP / Đồng bộ thời gian:**
   - etcd và Kubernetes TLS certificates đòi hỏi độ lệch đồng hồ (clock skew) giữa các Node phải < 500ms. Bắt buộc kích hoạt `chronyd` hoặc `systemd-timesyncd` trên cả 4 VM.

- **CNI đề xuất:** Flannel v0.26.1 kết hợp NetworkPolicy controller (Kube-router hoặc Calico IPAM).

## 9. Tích hợp Case Study: Spark Network Incident (Bài 27)

- **Ứng dụng:** Apache Spark 3.5.3 on Kubernetes (Native Cluster Mode, Scala 2.12.18).
- **Kiến trúc hai chiều (Bi-directional Data & Control Planes):**
  - Driver pod khởi tạo tại `Worker-1`, Executor pods phân bổ tại `Worker-2` và `Worker-3`.
  - Executor dùng Headless Service FQDN (`spark-*-driver-svc.namespace.svc`) để resolve ra IP của Driver.
  - Executor mở kết nối TCP tới Driver qua:
    1. Port `7078` (Driver RPC): Đăng ký Executor ID và nhận lịch trình Task.
    2. Port `7079` (Driver BlockManager): Truyền nhận dữ liệu khối broadcast và shuffle.
- **Sự cố thực tế đã xử lý (Bài 27b):**
  - Triệu chứng: 5 Executor pod liên tục crash với exit code `Error` / `Connection refused: ...:7078`.
  - Phân biệt bản chất:
    - DNS Resolution thành công (FQDN phân giải ra đúng IP Driver `10.42.3.91`).
    - Lỗi là TCP Layer 4 `Connection refused` (nhận gói RST do NetworkPolicy trên Driver chỉ mở port 4040 cho Web UI, chặn 7078 và 7079).
    - Không phải lỗi OOMKilled (ExitCode 137).
  - Khắc phục & Regression Check: Mở cả 2 port `7078` và `7079` trong spec Ingress của NetworkPolicy. Toàn bộ Executor đăng ký thành công, truyền nhận broadcast data thông suốt, tính toán giá trị `Pi is roughly 3.14169` và kết thúc với status `Completed`.
- **Tham chiếu chi tiết:** Báo cáo sự cố chuyên sâu [notes/incident-27b-spark.md](incident-27b-spark.md) và ghi chú [notes/27b.md](27b.md).

### Kết luận Network Readiness:
Cụm 4 VM Ubuntu trên VMware **ĐỦ ĐIỀU KIỆN SẴN SÀNG CÓ ĐIỀU KIỆN (CONDITIONAL READY)** để triển khai Kubernetes Data Platform, với điều kiện team VMware và Network phê duyệt và cấu hình 2 mục tiên quyết trong ticket:
1. Đảm bảo port `UDP 8472` thông suốt giữa 4 VM và nâng MTU vSwitch lên `>= 1600` (Jumbo Frames).
2. Chấp thuận cấu hình `MAC Address Changes: Accept` và `Forged Transmits: Accept` trên Port Group riêng của cụm.
