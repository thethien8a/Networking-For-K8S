# 19b — Lần theo Pod resolver → DNS Service → CoreDNS

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-11-09 14:24
- Thời lượng: 30 phút
- Máy thực thi / OS / cluster context / namespace: macOS (Host) -> cluster `k3d-de-k3d`, namespace `nfk-19b` (đã dọn dẹp sạch)
- Phiên bản và tài liệu đã đối chiếu: K3s v1.33.6+k3s1, containerd 2.1.5-k3s1.33, CoreDNS Service `kube-dns` ClusterIP `10.43.0.10`, CoreDNS Pod IP `10.42.0.38` trên `k3d-de-k3d-server-0`, Linux kernel 7.2.12-orbstack; [Debugging DNS Resolution](https://kubernetes.io/docs/tasks/administer-cluster/dns-debugging-resolution/)
- Phạm vi được phép thay đổi: Namespace riêng `nfk-19b`, Pods `client`, `backend`, Service `backend-svc`

## Mục tiêu

- Lần theo đường đi thực tế của gói tin DNS: Socket client (UDP 53) -> Service `kube-dns` (`10.43.0.10`) -> iptables DNAT -> CoreDNS Pod (`10.42.0.38:53`) -> Return path.
- Phân biệt bản chất rạch ròi giữa `NXDOMAIN` (Server sống khỏe, phản hồi 0ms, bản ghi không tồn tại) với `connection timed out / no servers could be reached` (gói tin bị drop dọc đường hoặc CoreDNS chết).
- Thực hành phương pháp chẩn đoán DNS không xâm lấn (non-invasive triage): Kiểm tra hạ tầng CoreDNS từ bên ngoài qua Service/EndpointSlice/Pod status mà không cần restart/sửa deployment ứng dụng.
- Điều tra sự cố Break & Fix ẩn danh: Bóc tách lỗi `nameserver` sai trong `/etc/resolv.conf`, dùng direct ClusterIP làm control test loại trừ Data Plane, hoàn nguyên và nghiệm thu 200 OK.

## Dự đoán trước lab

| Phép thử | Kết quả dự đoán | Vì sao / giả định |
|---|---|---|
| Query tên sai vs Query khi DNS sập | Tên sai ra NXDOMAIN (0ms); DNS sập ra Timeout (5s) | NXDOMAIN là phản hồi chính thức từ DNS server; Timeout là do gói tin bị drop hoặc server không trả lời |
| ClusterIP curl được nhưng Service Name lỗi | Hạ tầng CoreDNS hoặc DNS config của client lỗi | Direct ClusterIP chứng minh Data plane/kube-proxy/backend sống; lỗi chỉ nằm ở tầng phân giải tên |

```bash

# 2. Baseline đo kiểm tên đúng, tên sai và direct HTTP

kubectl exec -n nfk-19b client -- nslookup non-existent-service.nfk-19b.svc.cluster.local.
```

### 2. Bằng chứng Baseline
```text
# Query tên đúng:
Name:   backend-svc.nfk-19b.svc.cluster.local
Address: 10.43.165.246

# Query tên sai (NXDOMAIN phản hồi 0ms):
Server:         10.43.0.10
Address:        10.43.0.10:53
** server can't find non-existent-service.nfk-19b.svc.cluster.local.: NXDOMAIN

# Direct curl qua Service:
Backend 19b responding
```

### 3. Bằng chứng Sự cố Break & Fix
- Phân giải tên bị treo và timeout:
  ```text
  ;; connection timed out; no servers could be reached
  command terminated with exit code 1
  ```
- Control test gọi trực tiếp qua ClusterIP vẫn sống khỏe 200 OK:
  ```text
  $ kubectl exec -n nfk-19b client -- curl -s 10.43.165.246:80
  Backend 19b responding
  ```
- Đọc `/etc/resolv.conf` bắt quả tang `nameserver` sai:
  ```text
  search nfk-19b.svc.cluster.local svc.cluster.local cluster.local
  nameserver 10.43.0.250
  options timeout:2 attempts:1 ndots:5
  ```

### 4. Bằng chứng Sau khi Sửa lỗi
- Kubelet gán lại `nameserver 10.43.0.10` chuẩn:
  ```text
  search nfk-19b.svc.cluster.local svc.cluster.local cluster.local
  nameserver 10.43.0.10
  options ndots:5
  ```
- Phân giải tức thì và HTTP request 200 OK:
  ```text
  Name:   backend-svc.nfk-19b.svc.cluster.local
  Address: 10.43.25.189

  $ kubectl exec -n nfk-19b client -- curl -s backend-svc
  Backend 19b responding
  ```

## Lỗi gặp phải và phân tích root cause

| Triệu chứng | Giả thuyết | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| Query tên Service bị `connection timed out; no servers could be reached` sau vài giây | 1. Pod backend chết<br>2. CoreDNS sập<br>3. Pod resolver trỏ sai nameserver / NetworkPolicy chặn UDP 53 | - Control test `curl <ClusterIP>:80`<br>- `kubectl get pods -n kube-system -l k8s-app=kube-dns`<br>- `cat /etc/resolv.conf` bên trong Pod | - Control test ra 200 OK (loại trừ giả thuyết 1)<br>- CoreDNS Pod vẫn Running 1/1 (loại trừ giả thuyết 2)<br>- `cat /etc/resolv.conf` thấy `nameserver 10.43.0.250` không tồn tại -> Xác nhận Root Cause 3! |

## Cách sửa và bằng chứng xác minh

- Khôi phục Pod `client` về chính sách DNS mặc định `dnsPolicy: ClusterFirst` thông qua `kubectl replace --force -f lab-19b.yaml`.
- Kubelet tự động đưa `nameserver 10.43.0.10` trở lại.
- Nghiệm thu: `nslookup backend-svc` trả về IP `10.43.25.189` tức thì; `curl -s backend-svc` trả về `Backend 19b responding` (200 OK).

## Rollback / dọn dẹp / tài nguyên còn giữ

- Lệnh thực thi dọn dẹp: `kubectl delete ns nfk-19b --timeout=30s && rm -f lab-19b.yaml` (LLM thực hiện).
- Kiểm tra sau dọn dẹp: `kubectl get ns nfk-19b` xác nhận namespace đã xóa hoàn toàn.

## Review và tự giải thích

- **3 điều hiểu được:**
  1. `NXDOMAIN` là câu trả lời hợp lệ và tích cực từ CoreDNS, chứng minh mạng và DNS server sống khỏe; ngược lại `connection timed out` chỉ ra gói tin bị drop hoặc DNS server không phản hồi.
  2. Đường đi của gói tin DNS luôn qua Service `kube-dns` (ClusterIP `10.43.0.10`) trước khi được Netfilter iptables DNAT sang Pod IP của CoreDNS (`10.42.0.38`).
  3. Phương pháp dùng Direct ClusterIP làm Control Test giúp khoanh vùng ngay lập tức sự cố nằm ở tầng DNS hay ở tầng ứng dụng/data plane mà không cần restart Pod.
- **2 điều còn thắc mắc:**
  1. Trong cụm production lớn, CoreDNS thường được cấu hình Autoscaler (cluster-proportional-autoscaler) theo số lượng Node và Core như thế nào?
  2. Sự khác biệt về hiệu năng và cơ chế hoạt động khi triển khai NodeLocal DNSCache (daemonset chạy DNS cache cục bộ trên từng node) so với gọi trực tiếp CoreDNS Service.
- **1 thử nghiệm tiếp theo:**
  - Thực hành chẩn đoán 2 mini-incidents về Service ở bài 20a.
- **Câu áp dụng sang tình huống khác (Data Platform Triage):**
  - Khi một Spark Executor hoặc Airflow worker báo `java.net.UnknownHostException` hoặc `timed out resolving host`: Ngay lập tức exec vào pod kiểm tra `cat /etc/resolv.conf` và chạy `getent hosts <target-host>` kết hợp control test curl bằng IP để cô lập xem sự cố thuộc về CoreDNS cụm hay cấu hình client.
