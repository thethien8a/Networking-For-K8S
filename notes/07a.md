# 07a — Từ hostname qua resolver đến DNS record

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-10-26 23:50
- Thời lượng: 40 phút
- Máy thực thi / OS / cluster context / namespace: macOS Darwin arm64 (Mac mini), Docker runtime (OrbStack engine), Linux aarch64 container environment.
- Phiên bản và tài liệu đã đối chiếu:
  - CoreDNS: v1.10.1 (chuẩn DNS server trong Kubernetes)
  - Bind-tools: 9.20.30 (`dig`)
  - Curl: 8.23.0
- Phạm vi được phép thay đổi: Toàn quyền trên mạng `nfk-07a` và các container lab `nfk-07a-*`.

## Mục tiêu

- Nhận diện các bản ghi DNS cơ bản: A, AAAA, CNAME, cơ chế TTL và status code (NOERROR, NXDOMAIN).
- Phân biệt cơ chế phân giải tên của OS Resolver (`/etc/hosts`, `getent`, `curl`, Spark/JVM) với công cụ kiểm tra DNS trực tiếp (`dig`, `nslookup`).
- Nắm rõ cơ chế search domain và tham số `ndots` (đặc biệt là `ndots:5` trong Kubernetes).
- Điều tra và xử lý lỗi Dangling CNAME (chuỗi CNAME trỏ vào bản ghi đích không tồn tại).

## Dự đoán trước lab

| Phép thử | Kết quả dự đoán | Vì sao / giả định | Khớp thực tế |
|---|---|---|---|
| Tên có trong `/etc/hosts` nhưng không có trên DNS server | `ping` / ứng dụng tìm ra IP; `dig` báo lỗi không tìm thấy | `ping` đi qua OS Resolver đọc `/etc/hosts`; `dig` hỏi thẳng DNS server bỏ qua file hosts | Đúng 100% |
| DNS resolve thành công địa chỉ IP | Không bảo đảm kết nối TCP thành công | DNS chỉ phân giải tên miền (L7); TCP có thể bị chặn bởi firewall (DROP), port chưa mở (RST), hoặc IP đã chết | Đúng 100% |

## Các bước thực hành / câu lệnh

### 1. Khám phá cấu hình Resolver
- Lệnh:
  ```bash
  docker exec nfk-07a-client cat /etc/resolv.conf
  docker exec nfk-07a-client cat /etc/hosts
  ```
- Kết quả quan sát:
  - `nameserver 127.0.0.11`: Docker embedded DNS stub resolver (chuyển tiếp tiếp sang CoreDNS `10.250.70.53`).
  - `search lab.internal`: Search domain tự động bổ sung cho các tên ngắn.
  - `/etc/hosts`: Chứa ánh xạ tĩnh `10.250.70.99 custom.local`.

### 2. Truy vấn DNS Record với `dig`
- Lệnh:
  ```bash
  docker exec nfk-07a-client dig db.lab.internal
  docker exec nfk-07a-client dig analytics.lab.internal
  ```
- Kết quả:
  - `db.lab.internal`: Type `A`, TTL `60`, status `NOERROR`, IP `10.250.70.10`.
  - `analytics.lab.internal`: Type `CNAME` trỏ tới `db.lab.internal.`; CoreDNS giải tiếp luôn bản ghi `A` của `db.lab.internal.` thành `10.250.70.10` trong `ANSWER SECTION`.

### 3. Đối chứng `/etc/hosts` vs `dig`
- Lệnh:
  ```bash
  docker exec nfk-07a-client dig custom.local
  docker exec nfk-07a-client getent hosts custom.local
  ```
- Kết quả:
  - `dig custom.local`: Trả về `status: NXDOMAIN`, không có `ANSWER SECTION`.
  - `getent hosts custom.local`: Trả về `10.250.70.99 custom.local`.
  - Kết luận: `dig` độc lập và bỏ qua `/etc/hosts`.

### 4. Kiểm tra ứng dụng HTTP và Host Header
- Lệnh:
  ```bash
  docker exec nfk-07a-client curl -s http://10.250.70.10:8080/
  docker exec nfk-07a-client curl -s http://db:8080/
  docker exec nfk-07a-client curl -s http://analytics.lab.internal:8080/
  ```
- Kết quả:
  - Gọi IP trực tiếp: Server nhận `Host: 10.250.70.10:8080`.
  - Gọi tên ngắn `db`: Nhờ `search lab.internal`, client tự phân giải thành `db.lab.internal`, server nhận `Host: db:8080`.
  - Mở rộng lý thuyết: Giải mã chi tiết cơ chế `ndots` (mặc định Linux `ndots:1`, trong Kubernetes `options ndots:5`) và kỹ thuật dùng FQDN dấu chấm đuôi `domain.com.` để tránh DNS amplification / roundtrips.

## Lỗi gặp phải và phân tích root cause (Break & Fix)

| Triệu chứng | Giả thuyết đồng nghiệp | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| `curl http://warehouse.lab.internal:8080/` báo lỗi `curl: (6) Could not resolve host (Domain name not found)` | CoreDNS bị chết / rớt mạng container | Chạy `dig warehouse.lab.internal` để xem CoreDNS có phản hồi và xem cấu trúc bản ghi | CoreDNS phản hồi ngay lập tức (không chết). `warehouse.lab.internal` là CNAME trỏ tới `dw-legacy.lab.internal.`, nhưng tên đích này không có bản ghi A nào (Dangling CNAME / Broken CNAME Chain). |

## Cách sửa và bằng chứng xác minh

- Nguyên nhân gốc rễ là Dangling CNAME: bản ghi đích `dw-legacy.lab.internal.` chưa được tạo bản ghi `A`.
- Khắc phục: Tạo bản ghi `A` cho `dw-legacy.lab.internal.` hoặc trỏ CNAME của `warehouse` sang tên miền đích hợp lệ (ví dụ `db.lab.internal.`).

## Review và tự giải thích

- 3 điều hiểu được:
  1. OS Resolver (`/etc/hosts`, `getent`, app) và DNS CLI (`dig`, `nslookup`) là hai cơ chế khác nhau: `dig` bỏ qua `/etc/hosts`.
  2. DNS Resolve thành công chỉ đảm bảo dịch được tên sang IP, không đảm bảo cổng TCP hay ứng dụng đích hoạt động.
  3. Cơ chế search domain tự động ghép đuôi theo tham số `ndots`; lỗi Dangling CNAME xảy ra khi CNAME trỏ tới target không có bản ghi A.
- 2 điều còn thắc mắc: (Đã được giải đáp trực tiếp trong bài về `ndots:5` và Virtual Hosting Host header).
- 1 thử nghiệm tiếp theo: Bài 07b — Điều tra sự cố gọi IP chạy nhưng gọi hostname bị lỗi.
- Câu áp dụng sang tình huống khác:
  - Tình huống Spark Master cấu hình `/etc/hosts` chạy tốt nhưng `nslookup` báo `NXDOMAIN`. Học viên giải thích đúng: Spark Driver dùng OS Resolver đọc file hosts nên tìm thấy IP; `nslookup` hỏi thẳng DNS server nên báo NXDOMAIN. Mạng hoàn toàn bình thường.
- Mức gợi ý cao nhất: Tự giải quyết / gợi ý quan sát bản ghi bằng `dig`.
