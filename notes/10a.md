# 10a — Network namespace và veth pair

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-11-03 09:00
- Thời lượng: 40 phút
- Máy thực thi / OS / cluster context / namespace: macOS Darwin arm64 (OrbStack engine), Docker container `nfk-10a-lab` (Linux Alpine 3.24, image `nfk-07b-tools:local`, `--cap-add NET_ADMIN --cap-add SYS_ADMIN`). Network namespaces: `ns-a` và `ns-b`.
- Phiên bản và tài liệu đã đối chiếu:
  - ip-netns(8): https://man7.org/linux/man-pages/man8/ip-netns.8.html
  - veth(4) - Virtual Ethernet Device: https://man7.org/linux/man-pages/man4/veth.4.html
  - Kubernetes Network Model: https://kubernetes.io/docs/concepts/services-networking/
- Phạm vi được phép thay đổi: Container `nfk-10a-lab`, các namespace `ns-a`, `ns-b`, veth interfaces.

## Mục tiêu

- Hiểu rõ network namespace isolation khác process isolation như thế nào.
- Tạo hai namespace `ns-a` và `ns-b` nối trực tiếp bằng một `veth pair`, chuyển đúng đầu interface vào từng namespace.
- Đo kiểm và đối chứng trạng thái interface, kết nối L3 (ping) và L7 (HTTP).
- Kiểm chứng sự cô lập hoàn toàn của loopback (`lo`) và bảng socket (`ss -lnt`) giữa các namespace và host.
- **Bắt buộc liên hệ với cụm Kubernetes:** Hiểu rõ mối liên hệ giữa Linux Network Namespace với Pod, veth pair với CNI và Node, cũng như ứng dụng debug thực tế (như kiểm tra trạng thái NO-CARRIER khi Pod chết).

## Dự đoán trước lab

| Phép thử | Kết quả dự đoán | Vì sao / giả định | Khớp thực tế |
|---|---|---|---|
| Server listen loopback trong namespace A (`127.0.0.1:8080`), từ namespace B có truy cập được không? | Không | Loopback (`lo`) là tài nguyên cục bộ độc lập của từng namespace, không đi qua veth pair | Đúng 100% |
| Gán IP nhưng interface chưa bật UP (`DOWN`), lệnh ping sẽ ra sao? | Thất bại | Kernel không kích hoạt connected route trên link DOWN và từ chối gửi packet ra L2 | Đúng 100% (`Network unreachable`) |

## Các bước thực hành / câu lệnh

Học viên trực tiếp thực thi trên terminal macOS qua Docker CLI:

```bash
# 1. Khởi tạo container môi trường Linux có NET_ADMIN và SYS_ADMIN
docker run -d --name nfk-10a-lab --cap-add NET_ADMIN --cap-add SYS_ADMIN nfk-07b-tools:local sleep infinity

# 2. Tạo 2 network namespace
docker exec nfk-10a-lab ip netns add ns-a
docker exec nfk-10a-lab ip netns add ns-b

# 3. Tạo veth pair ở host và chuyển từng đầu vào namespace
docker exec nfk-10a-lab ip link add veth-a type veth peer name veth-b
docker exec nfk-10a-lab ip link set veth-a netns ns-a
docker exec nfk-10a-lab ip link set veth-b netns ns-b

# 4. Gán IP cho 2 đầu
docker exec nfk-10a-lab ip netns exec ns-a ip addr add 10.100.1.1/24 dev veth-a
docker exec nfk-10a-lab ip netns exec ns-b ip addr add 10.100.1.2/24 dev veth-b

# 5. Kiểm chứng link DOWN: ping báo Network unreachable
docker exec nfk-10a-lab ip netns exec ns-a ping -c 1 10.100.1.2

# 6. Bật UP veth và loopback
docker exec nfk-10a-lab ip netns exec ns-a ip link set veth-a up
docker exec nfk-10a-lab ip netns exec ns-a ip link set lo up
docker exec nfk-10a-lab ip netns exec ns-b ip link set veth-b up
docker exec nfk-10a-lab ip netns exec ns-b ip link set lo up

# 7. Đo kiểm L3 ping
docker exec nfk-10a-lab ip netns exec ns-a ping -c 2 10.100.1.2

# 8. Chạy HTTP server tại ns-a và đo kiểm L7 từ ns-b
docker exec -d nfk-10a-lab ip netns exec ns-a python3 -m http.server 8080
docker exec nfk-10a-lab ip netns exec ns-b curl -s -I http://10.100.1.1:8080/ | head -n 1

# 9. Đo kiểm Socket & Loopback Isolation
docker exec nfk-10a-lab ip netns exec ns-b curl -s -I --connect-timeout 2 http://127.0.0.1:8080/
docker exec nfk-10a-lab ip netns exec ns-a ss -lnt
docker exec nfk-10a-lab ip netns exec ns-b ss -lnt
docker exec nfk-10a-lab ss -lnt
```

## Bằng chứng thực tế thu thập được

1. **Khởi tạo và cắm veth pair:**
   ```text
   ns-a: lo DOWN, veth-a@if3 DOWN ea:7e:de:81:b2:14
   ns-b: lo DOWN, veth-b@if4 DOWN 2a:bb:2f:cd:89:fc
   ```
   Interface peer index chỉ rõ `@if3` tương ứng index 4 bên `ns-b` và ngược lại.

2. **Dự đoán B được xác nhận:** Khi link ở trạng thái `DOWN`, gán IP nhưng ping báo lỗi:
   ```text
   PING 10.100.1.2 (10.100.1.2): 56 data bytes
   ping: sendto: Network unreachable
   ```

3. **Bật UP và ping L3 thành công:**
   ```text
   PING 10.100.1.2 (10.100.1.2): 56 data bytes
   64 bytes from 10.100.1.2: seq=0 ttl=64 time=0.122 ms
   64 bytes from 10.100.1.2: seq=1 ttl=64 time=0.107 ms
   2 packets transmitted, 2 packets received, 0% packet loss
   ```

4. **Kết nối L7 HTTP và Socket Isolation:**
   - Client `ns-b` curl sang `http://10.100.1.1:8080/` thành công: `HTTP/1.0 200 OK`.
   - Client `ns-b` curl vào `http://127.0.0.1:8080/` thất bại (chứng minh loopback isolation).
   - Socket table: `LISTEN 0.0.0.0:8080` chỉ xuất hiện duy nhất ở `ns-a`, hoàn toàn trống ở `ns-b` và `host` (chứng minh socket table isolation).

## Lỗi gặp phải và phân tích root cause (Break & Fix)

| Triệu chứng | Giả thuyết | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| Client `ns-b` curl sang `10.100.1.1:8080` thất bại | Link DOWN, mất veth hoặc process chết | Chạy `ping` và `ip -br link` ở cả 2 bên | `veth-b` trong `ns-b` ở trạng thái `DOWN`; `veth-a` ở `ns-a` báo `<NO-CARRIER...>` |

**Phân tích kỹ thuật (Root Cause):**
`veth pair` hoạt động theo cặp đối tác. Khi `veth-b` bị admin set DOWN, đầu đối diện `veth-a` mất carrier vật lý ảo (gắn cờ `NO-CARRIER`). Mặc dù admin state của `veth-a` vẫn là UP, operstate bị chuyển thành DOWN do mất carrier, làm toàn bộ đường truyền L2 bị ngắt.

## Cách sửa và bằng chứng xác minh

- Lệnh sửa tối thiểu:
  ```bash
  docker exec nfk-10a-lab ip netns exec ns-b ip link set veth-b up
  ```
- Bằng chứng phục hồi:
  - Cờ `NO-CARRIER` trên `veth-a` tự động biến mất, chuyển thành `<BROADCAST,MULTICAST,UP,LOWER_UP>`.
  - Kết nối HTTP phục hồi ngay lập tức:
    ```text
    HTTP/1.0 200 OK
    ```

## Review và tự giải thích

- **3 điều hiểu được:**
  1. Một Kubernetes Pod thực chất chính là một Linux Network Namespace; các container trong cùng Pod dùng chung namespace này nên chia sẻ chung loopback `127.0.0.1` và bảng port.
  2. `veth pair` đóng vai trò là sợi cáp mạng ảo hai đầu mà CNI dùng để kết nối Pod với Node / Bridge.
  3. Cơ chế Carrier của veth: một đầu bị tắt khiến đầu kia bị `NO-CARRIER`; khi bật lại đầu bị tắt, đường truyền tự động sáng đèn xanh (`LOWER_UP`) nếu đầu kia đã sẵn sàng.
- **Câu hỏi áp dụng:** Khi container Spark Executor bị OOM chết, interface veth tương ứng trên Node sẽ báo cờ gì?
  - Học viên trả lời chính xác: **`NO-CARRIER`**.
