# 25a — Pod egress, source address và SNAT

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-11-17 15:45
- Thời lượng: 45 phút
- Máy thực thi / OS / cluster context / namespace: Mac `SSC1s-Mac-mini-4.local` (Darwin arm64) | k3d v5.8.3 | context `k3d-de-k3d` | namespace `nfk-25a` (đã rollback dọn sạch hoàn toàn)
- Phiên bản và tài liệu đã đối chiếu: K3s `v1.33.6+k3s1`, Flannel CNI, iptables Netfilter MASQUERADE
- Phạm vi được phép thay đổi: External container `nfk-25a-ext-server`, namespace `nfk-25a` (`client-pod`), chain `FLANNEL-POSTRTG` trên `k3d-de-k3d-agent-0`

## Mục tiêu

- So sánh reachability từ Pod và từ Node tới cùng một external endpoint ngoài cluster.
- Xác định source address bên ngoài quan sát được và phân tích rạch ròi cơ chế SNAT (MASQUERADE) tại Netfilter POSTROUTING.
- Nhận diện và xử lý sự cố đứt gãy kết nối Egress khi mất SNAT (Return Path blackhole).

## Dự đoán trước lab

| Phép thử | Kết quả dự đoán của học viên | Đánh giá & phân tích thực tế | Kết quả thực tế |
|---|---|---|---|
| Node vs Pod gọi External Server | Source IP nhìn thấy giống nhau | Kết quả giống nhau (Node IP `192.168.155.3`), nhưng cơ chế khác nhau: Node không qua NAT, Pod phải qua SNAT Netfilter | Khớp: Node: `192.168.155.3:59806`, Pod: `192.168.155.3:24792` |
| Mất SNAT: Pod gọi External Server | Timeout vì gói không ra ngoài được, bị drop | Chưa chính xác nguyên nhân: Gói TCP SYN vẫn ra ngoài được, nhưng bị drop ở chiều về (Return Path) do External Server không có route về Pod IP | Chuẩn xác triệu chứng: Timeout sau 2s (`exit code 28`) |
| Mất SNAT: Node gọi External Server | Bị ảnh hưởng | Sai: Node dùng chính IP của nó, không cần SNAT nên không bị ảnh hưởng | Chuẩn xác: Node vẫn gọi thành công 200 OK |

## Topology và địa chỉ IP

```text
[ Pod: client-pod ] (IP: 10.42.3.79)
     │
     ▼ (veth pair -> cni0)
[ Node: k3d-de-k3d-agent-0 ] (IP: 192.168.155.3)
     │
     ├──(1. Internal Pod-to-Pod/DNS: 10.42.0.0/16)──> Rule 2: RETURN (Bảo toàn Pod IP)
     │
     └──(2. Egress ra ngoài cụm: !224.0.0.0/4)────────> Rule 5: MASQUERADE (SNAT thành 192.168.155.3)
                                                                 │
                                                                 ▼ (Gói tin rời Node)
                                                   [ External Mock Server ]
                                                   (IP: 192.168.155.6:8080)
                                                   (Nhìn thấy Source IP: 192.168.155.3)
```

## Các bước thực hành / câu lệnh

1. **Khởi tạo External Mock Server và Client Pod:**
   - External server: `python:3.12-alpine` chạy HTTP echo client IP trên Docker network `k3d-de-k3d` (`192.168.155.6:8080`).
   - Pod `client-pod`: Image `curlimages/curl:8.10.1` nằm trên worker `k3d-de-k3d-agent-0`, IP `10.42.3.79`.
2. **Đo kiểm Baseline:**
   - Từ Node `agent-0`: `docker exec k3d-de-k3d-agent-0 wget -qO- http://192.168.155.6:8080` -> Client IP: `192.168.155.3:59806`.
   - Từ Pod `client-pod`: `kubectl -n nfk-25a exec client-pod -- curl -s http://192.168.155.6:8080` -> Client IP: `192.168.155.3:24792`.
3. **Khảo sát bảng iptables NAT trên Node:**
   - Lệnh: `docker exec k3d-de-k3d-agent-0 iptables -t nat -L FLANNEL-POSTRTG -v -n --line-numbers`.
   - Bắt quả tang Rule 2 (`RETURN` cho nội bộ cụm `10.42.3.0/24 -> 10.42.0.0/16`) và Rule 5 (`MASQUERADE` cho egress `10.42.0.0/16 -> !224.0.0.0/4`).
4. **Mô phỏng sự cố Break & Fix:**
   - Chèn rule bypass MASQUERADE: `iptables -t nat -I FLANNEL-POSTRTG 1 -s 10.42.3.0/24 -d 192.168.155.6 -j RETURN`.
   - Đo kiểm ma trận 3 chiều:
     - Node -> External: 200 OK.
     - Pod -> CoreDNS (10.43.0.10:53): Port open 200 OK (veth và CNI nội bộ khỏe).
     - Pod -> External: Connect Timeout sau 2s (`exit code 28`).
   - Bắt quả tang rule số 1 tăng bộ đếm `pkts=2`.
5. **Khắc phục và Phục hồi:**
   - Xóa rule lỗi: `docker exec k3d-de-k3d-agent-0 iptables -t nat -D FLANNEL-POSTRTG 1`.
   - Đo kiểm lại từ Pod: `HELLO FROM EXT-SERVER! Client IP seen: 192.168.155.3:13716` (Thành công).

## Bằng chứng

- **Baseline output:**
  - Node: `HELLO FROM EXT-SERVER! Client IP seen: 192.168.155.3:59806`
  - Pod: `HELLO FROM EXT-SERVER! Client IP seen: 192.168.155.3:24792`
  - Pod IP: `10.42.3.79` trên `k3d-de-k3d-agent-0`
- **Break & Fix output:**
  - Pod curl timeout: `command terminated with exit code 28`
  - iptables counter: `1 2 120 RETURN all -- * * 10.42.3.0/24 192.168.155.6`
- **Post-fix output:**
  - `HELLO FROM EXT-SERVER! Client IP seen: 192.168.155.3:13716`

## Lỗi gặp phải và phân tích root cause

| Triệu chứng | Giả thuyết | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| Pod curl ra ngoài Timeout (exit code 28) | External server sập hoặc đóng port | Gọi từ Node `agent-0` bằng `wget` | Bác bỏ: Node gọi 200 OK tức thì, server sống khỏe |
| Pod curl ra ngoài Timeout | Pod hỏng card mạng veth hoặc CNI hỏng | Gọi `nc -z -v -w 2 10.43.0.10 53` tới CoreDNS | Bác bỏ: Port open tức thì, data path nội bộ hoàn toàn tốt |
| Pod curl ra ngoài Timeout | Mất SNAT, gói ra ngoài mang Pod IP khiến mất đường về | Kiểm tra iptables nat `FLANNEL-POSTRTG` | Xác nhận root cause: Rule 1 `RETURN` khiến gói tin không bị MASQUERADE, External server không biết đường về cho `10.42.3.79` |

## Cách sửa và bằng chứng xác minh

- Lệnh sửa tối thiểu: `docker exec k3d-de-k3d-agent-0 iptables -t nat -D FLANNEL-POSTRTG 1`
- Đo kiểm sau sửa: `kubectl -n nfk-25a exec client-pod -- curl -s http://192.168.155.6:8080` trả về `200 OK` với `Client IP seen: 192.168.155.3:13716`.

## Rollback / dọn dẹp / tài nguyên còn giữ

- Container `nfk-25a-ext-server` đã được xóa sạch hoàn toàn (`docker rm -f`).
- Namespace `nfk-25a` đã được xóa sạch hoàn toàn khỏi cluster (`NotFound`).
- Chain `FLANNEL-POSTRTG` trên `agent-0` đã hoàn nguyên về trạng thái ban đầu của CNI Flannel. Không còn nợ rollback.

## Review và tự giải thích

- **3 điều học được:**
  1. Pod Egress ra ngoài mạng vật lý/Internet bắt buộc phải qua SNAT (MASQUERADE) tại hook Netfilter POSTROUTING của Node, vì mạng ngoài không có route về dải Pod overlay.
  2. Phân biệt rõ rệt hai luồng trong Flannel CNI: Lưu lượng nội bộ cụm (Pod-to-Pod) được khớp rule `RETURN` để giữ nguyên Pod IP; chỉ lưu lượng đi ra ngoài mới bị `MASQUERADE` sang Node IP.
  3. Chữ ký chẩn đoán mất SNAT: Node gọi ra ngoài 200 OK, Pod gọi nội bộ 200 OK, nhưng Pod gọi ra ngoài bị Connect Timeout (do mất Return Path).
- **Ứng dụng Data Engineering:**
  - Khi thiết lập firewall cho các Database/Data Warehouse bên ngoài (Oracle, Postgres, Snowflake), nếu Kubernetes dùng SNAT thì IP cần whitelist chính là IP của các Kubernetes Worker Node.
  - Trong môi trường Auto-scaling Node, việc Node IP thay đổi liên tục sẽ làm vỡ whitelist. Giải pháp thực tế là triển khai **Egress Gateway** (Cilium/Calico) hoặc NAT Gateway tĩnh trên Cloud để gom toàn bộ Pod Egress qua một IP tĩnh cố định.
