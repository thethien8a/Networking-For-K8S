# 25b — MTU, fragmentation và PMTU khi troubleshoot

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-11-17 17:25
- Thời lượng: 45 phút
- Máy thực thi / OS / cluster context / namespace: Mac `SSC1s-Mac-mini-4.local` (Darwin arm64) | k3d v5.8.3 | context `k3d-de-k3d` | namespace `nfk-25b` (đã rollback dọn sạch hoàn toàn)
- Phiên bản và tài liệu đã đối chiếu: K3s `v1.33.6+k3s1`, Flannel VXLAN overlay, iputils 20250605 (`ping`, `tracepath`), Netfilter mangle
- Phạm vi được phép thay đổi: Namespace tạm `nfk-25b` (`client-pod`, `server-pod`), chain `PREROUTING` trên `k3d-de-k3d-agent-0` (bảng `mangle`)

## Mục tiêu

- Phân biệt Interface MTU, Path MTU (PMTU), và kích thước payload ứng dụng (ICMP Payload, TCP MSS, HTTP Body).
- Thực chứng toán học và thực nghiệm ngưỡng phân mảnh: `Kích thước IP packet = ICMP payload + 28 bytes`.
- Điều tra sự cố kinh điển trong Kubernetes & Big Data: "Ping nhỏ thông, HTTP nhỏ 200 OK nhưng HTTP lớn hoặc tải batch dữ liệu bị treo timeout" (MTU Blackhole).
- Dùng ma trận đo kiểm phân biệt lỗi Application vs lỗi MTU đường truyền, loại bỏ các giả thuyết sai lầm.

## Topology và địa chỉ IP

```text
[ client-pod ] (IP: 10.42.3.81, MTU 1450)
      │ (veth -> cni0 MTU 1450)
[ Node: k3d-de-k3d-agent-0 ] (eth0 MTU 1500)
      │
      │ ◄── [ Chướng ngại vật mô phỏng: DROP packet > 1300 bytes trên mangle PREROUTING ]
      ▼
   (Mạng Overlay Flannel VXLAN UDP 8472: flannel.1 MTU 1450)
      ▲
      │
[ Node: k3d-de-k3d-agent-1 ] (eth0 MTU 1500)
      │ (cni0 -> veth MTU 1450)
[ server-pod ] (IP: 10.42.1.66, MTU 1450, HTTP Listener port 8080)
      ├── Endpoint /small: HTTP 200 OK ("SMALL OK", ~50 bytes)
      └── Endpoint /large: HTTP 200 OK (50000 bytes)
```

## Các bước thực hành / câu lệnh

1. **Khảo sát Inventory MTU trên cụm k3d:**
   - Lệnh: `docker exec k3d-de-k3d-agent-0 ip -d link show`.
   - Kết quả: `eth0`: 1500; `flannel.1`: 1450; `cni0`: 1450; `veth*`: 1450.
2. **Khởi tạo môi trường đo kiểm:**
   - Tạo namespace `nfk-25b`, build và nạp image `nfk-25b-tools:local` chứa bộ `iputils` (`ping` có `-M do`, `tracepath`).
   - Ghim `client-pod` trên `agent-0` (IP: `10.42.3.81`) và `server-pod` trên `agent-1` (IP: `10.42.1.66`).
3. **Đo kiểm ngưỡng phân mảnh Pod MTU 1450:**
   - Vừa khít MTU: `kubectl -n nfk-25b exec client-pod -- ping -c 2 -M do -s 1422 10.42.1.66` -> 2 received, 0% loss, rtt = 0.178 ms.
   - Vượt ngưỡng 1 byte: `kubectl -n nfk-25b exec client-pod -- ping -c 2 -M do -s 1423 10.42.1.66` -> `ping: sendmsg: Message too large`, 100% loss.
   - Dò Path MTU: `kubectl -n nfk-25b exec client-pod -- tracepath -n 10.42.1.66` -> `Resume: pmtu 1450 hops 3 back 3`.
4. **Mô phỏng sự cố Break & Fix (MTU Blackhole):**
   - Chạy HTTP Server trên `server-pod` cung cấp 2 endpoint `/small` và `/large`.
   - Gài rule drop packet lớn trên đường về tại `agent-0`: `iptables -t mangle -I PREROUTING -s 10.42.1.66 -m length --length 1300:65535 -j DROP`.
5. **Chẩn đoán sự cố ma trận 4 phép thử:**
   - Phép đo 1: `ping -c 2 10.42.1.66` -> 0% loss, thông mượt mà.
   - Phép đo 2: `curl /small` -> 200 OK ("SMALL OK").
   - Phép đo 3: `curl -v /large` -> TCP Handshake OK, HTTP Headers 200 OK, nhưng khi nhận body bị `Operation timed out after 3004 milliseconds with 0 bytes received`.
   - Phép đo 4: `ping -M do -s 1250` (IP 1278B) -> 0% loss; `ping -M do -s 1350` (IP 1378B) -> 100% loss.
6. **Xử lý và nghiệm thu:**
   - Soi counter: `docker exec k3d-de-k3d-agent-0 iptables -t mangle -L PREROUTING -v -n` -> Bắt quả tang 26 pkts (59780 bytes) bị DROP.
   - Sửa lỗi tối thiểu: `docker exec k3d-de-k3d-agent-0 iptables -t mangle -D PREROUTING 1`.
   - Nghiệm thu: `curl /large | wc -c` trả về đúng 50000 bytes; `ping -M do -s 1350` thông 0% loss.

## Bằng chứng

- Output ping ngưỡng 1422B:
  `PING 10.42.1.66 (10.42.1.66) 1422(1450) bytes of data.`
  `1430 bytes from 10.42.1.66: icmp_seq=1 ttl=62 time=0.132 ms`
- Output ping ngưỡng 1423B:
  `ping: sendmsg: Message too large`
  `PING 10.42.1.66 (10.42.1.66) 1423(1451) bytes of data.`
- Output curl lỗi MTU Blackhole:
  `* Established connection to 10.42.1.66 (10.42.1.66 port 8080)`
  `< HTTP/1.0 200 OK`
  `* Operation timed out after 3004 milliseconds with 0 bytes received`
- Output counter iptables mangle:
  `1    26 59780 DROP    all  --  *  *  10.42.1.66  0.0.0.0/0  length 1300:65535`
- Output nghiệm thu:
  `50000` bytes và `2 packets transmitted, 2 received, 0% packet loss`.

## Lỗi gặp phải và phân tích root cause

| Triệu chứng | Giả thuyết | Phép kiểm tra phân biệt | Bằng chứng / kết luận |
|---|---|---|---|
| Image kéo lỗi `nethoppers/net-tools` | Mạng node lỗi hoặc Docker Hub rate limit | Kiểm tra `kubectl get pods` thấy `ErrImagePull` | Tự đóng gói image nhẹ `nfk-25b-tools:local` nạp thẳng bằng `k3d image import`. |
| Gói tin 1423 bytes bị lỗi `Message too large` | Gói tin bị drop trên đường mạng Flannel | Kiểm tra cờ `-M do` và kích thước trong ngoặc đơn `1423(1451)` | Lỗi xuất phát từ chính Socket Kernel tại Pod vì $1451 > \text{MTU } 1450$. |
| Rule ban đầu đặt ở FORWARD bị lọt gói | Kube-router can thiệp | Kiểm tra chuỗi `KUBE-ROUTER-FORWARD` | Kube-router có rule `RELATED,ESTABLISHED ACCEPT` ở đầu chuỗi FORWARD; chuyển rule sang `mangle PREROUTING` để tái hiện chuẩn xác. |
| Ping thông nhưng `curl /large` timeout | Application lỗi / Memory leak / Deadlock | `curl -v` và `ping -M do -s 1350` | Server đã gửi xong Headers 200 OK; lỗi do các segment dữ liệu lớn bị drop âm thầm giữa đường (MTU Blackhole). |

## Cách sửa và bằng chứng xác minh

- Xóa rule DROP trên bảng mangle: `iptables -t mangle -D PREROUTING 1`.
- Kiểm tra lại luồng:
  - `curl /large` lập tức trả về 50000 bytes trong ~0.02s.
  - `ping -M do -s 1350` thông suốt 0% packet loss.

## Rollback / dọn dẹp / tài nguyên còn giữ

- Xóa namespace `nfk-25b` bằng `kubectl delete namespace nfk-25b --now` (đã xác nhận xóa sạch toàn bộ Pod và tài nguyên bên trong).
- Kiểm tra bảng `mangle PREROUTING` trên `agent-0`: không còn rule DROP nào.
- Xóa image tạm `nfk-25b-tools:local`.
- Trạng thái cluster hoàn toàn sạch sẽ, sẵn sàng cho bài 26a.

## Review và tự giải thích

- 3 điều hiểu được:
  1. Phân biệt Interface MTU (1450B), Path MTU (1450B), TCP MSS (1410B) và ICMP Payload (1422B). Gói tin IP luôn bằng Payload + 28 bytes.
  2. Ping nhỏ thành công (84B) không chứng minh được mạng thông suốt cho packet lớn.
  3. MTU Blackhole xảy ra khi packet lớn bị drop mà router trung gian không trả về ICMP Type 3 Code 4 (do firewall chặn ICMP), khiến TCP retransmit mãi dẫn tới Operation Timeout dù handshake thành công.
- 2 điều còn thắc mắc:
  1. Trong môi trường Cloud (AWS/GCP), cơ chế MSS Clamping được cấu hình ở đâu để khắc phục MTU mismatch tự động?
  2. Jumbo Frame (MTU 9000) trong Data Center giúp cải thiện throughput của Spark shuffle như thế nào?

  - Bài 26a — Incident triage: Ứng dụng toàn bộ tư duy bóc tách sự cố để triage sự cố mạng Kubernetes theo quy trình chuẩn.
