# 17b — Service không có backend: điều tra selector mismatch

- Ngày/giờ (Asia/Ho_Chi_Minh): 2026-11-07 15:12
- Thời lượng: 35 phút
- Máy thực thi / OS / cluster context / namespace: macOS (Host) -> cluster `k3d-de-k3d`, namespace `nfk-17a`
- Phiên bản: k3s v1.33.6+k3s1, containerd 2.1.5-k3s1.33, Linux kernel 7.2.12-orbstack
- Tài liệu đối chiếu: [Debug Service](https://kubernetes.io/docs/tasks/debug/debug-application/debug-service/) · [Labels and Selectors](https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/)
- Phạm vi được phép thay đổi: Namespace riêng `nfk-17a`, Pods `be-1`, `be-2`, `client`, Service `my-data-svc`

## Mục tiêu

- Quan sát cơ chế đồng bộ tức thì của `EndpointSlice Controller` khi nhãn của Pod hoặc selector của Service bị thay đổi.
- Bóc tách triệu chứng "Pod IP gọi được 200 OK nhưng ClusterIP bị Connection refused sau 0 ms".
- Sử dụng phương pháp luận có hệ thống: Control test -> Label Query -> Patch Service tối thiểu để phục hồi dịch vụ.

## Dự đoán trước lab

| Phép thử | Kết quả dự đoán | Vì sao / giả định |
|---|---|---|
| Đổi nhãn `be-2` sang `app=other-service` | EndpointSlice loại bỏ IP `be-2`, 100% request đổ về `be-1` | EndpointSlice Controller phát hiện `be-2` không còn thỏa mãn selector, tự động gỡ IP |
| Pod IP 200 OK nhưng ClusterIP lỗi | Lỗi ở tầng Service/Kube-proxy; chưa loại trừ selector mismatch, targetPort sai, Pod NotReady | Pod backend và CNI route khỏe; tầng điều phối Virtual IP của Kubernetes gặp vấn đề |

## Topology và địa chỉ IP

```text
[ client ] (10.42.1.23 trên k3d-de-k3d-agent-1)
    │
    ▼ (gọi HTTP 10.43.204.13:80)
[ my-data-svc ]
  selector: app=data-service, env=prod  <-- LỖI LỆCH NHÃN (Pod mang env=lab)
    │
    ▼
[ EndpointSlice ] -> ENDPOINTS <unset> (rỗng!)
    │
    ▼
[ kube-proxy / iptables ] -> Kích hoạt rule REJECT (TCP RST) sau 0 ms
```

- **Pod backend:**
  - `be-1`: IP `10.42.3.29:8080`, Labels: `app=data-service, env=lab`
  - `be-2`: IP `10.42.1.22:8080`, Labels: `app=data-service, env=lab`
- **Service:** `my-data-svc` (ClusterIP `10.43.204.13:80`)

## Các bước thực hành / câu lệnh

### Bước 1: Đổi nhãn `be-2` và kiểm chứng phân bổ
```bash
kubectl label pod -n nfk-17a be-2 app=other-service --overwrite
kubectl get endpointslice -n nfk-17a
kubectl exec -n nfk-17a client -- sh -c 'for i in $(seq 1 6); do curl -s 10.43.204.13:80; done'
kubectl label pod -n nfk-17a be-2 app=data-service --overwrite
```

### Bước 2: Break & Fix điều tra sự cố ẩn
1. Bắt triệu chứng tại client:
   ```bash
   kubectl exec -n nfk-17a client -- curl -v --connect-timeout 2 10.43.204.13:80
   ```
2. Control test kiểm tra trực tiếp Pod IP:
   ```bash
   kubectl exec -n nfk-17a client -- curl -s 10.42.3.29:8080
   kubectl exec -n nfk-17a client -- curl -s 10.42.1.22:8080
   ```
3. Bóc tách selector và nhãn:
   ```bash
   kubectl get endpointslice -n nfk-17a
   kubectl get svc my-data-svc -n nfk-17a -o jsonpath='{.spec.selector}' && echo ""
   kubectl get pods -n nfk-17a --show-labels
   ```
4. Sửa chữa tối thiểu và nghiệm thu:
   ```bash
   kubectl patch svc my-data-svc -n nfk-17a -p '{"spec":{"selector":{"app":"data-service","env":"lab"}}}'
   kubectl get endpointslice -n nfk-17a
   kubectl exec -n nfk-17a client -- sh -c 'for i in $(seq 1 4); do curl -s 10.43.204.13:80; done'
   ```

## Bằng chứng

### 1. Đổi nhãn `be-2` -> EndpointSlice chỉ còn `be-1`

Output 6 requests:

### 2. Triệu chứng sự cố Break & Fix

* Failed to connect to 10.43.204.13 port 80 after 0 ms: Could not connect to server

### 3. Control test trực tiếp Pod IP
```text
curl -s 10.42.3.29:8080 -> Hello from Backend 1

### 4. Đối chứng nhãn
- Service selector: `{"app":"data-service","env":"prod"}` (phép giao logic AND)
- Pod labels: `app=data-service,env=lab` -> Lệch nhãn `env` dẫn tới EndpointSlice rỗng (`<unset>`).

my-data-svc-w8l2l   IPv4          8080    10.42.1.22,10.42.3.29   73m

Hello from Backend 2
Hello from Backend 1
Hello from Backend 2
Hello from Backend 1
```

## Lỗi gặp phải và phân tích root cause

- **Triệu chứng:** Client nhận `Connection refused` (0 ms) khi gọi Service qua ClusterIP.
- **Giả thuyết loại trừ:** Pod backend bị crash hoặc đóng port (loại trừ nhờ control test Pod IP 200 OK); CNI bị ngắt (loại trừ vì ping/curl Pod-to-Pod thông).
- **Root Cause:** Service `my-data-svc` bị cấu hình thừa nhãn `env=prod` trong `spec.selector`. Do Kubernetes áp dụng điều kiện AND trên toàn bộ nhãn trong selector, không có Pod nào thỏa mãn, dẫn tới `EndpointSlice Controller` xóa toàn bộ backend.

## Cách sửa và bằng chứng xác minh

- **Cách sửa:** Chạy `kubectl patch svc my-data-svc -n nfk-17a -p '{"spec":{"selector":{"app":"data-service","env":"lab"}}}'` để đưa selector về đúng tập nhãn của Pod backend.
- **Xác minh:** EndpointSlice phục hồi lập tức 2 endpoints `10.42.1.22:8080` và `10.42.3.29:8080`; traffic curl từ client chia đều qua cả 2 backend.

## Rollback / dọn dẹp / tài nguyên còn giữ

- **Dọn dẹp:** Toàn bộ namespace `nfk-17a` đã được LLM xóa sạch sẽ qua lệnh `kubectl delete ns nfk-17a`.
- **Kiểm tra sau dọn:** `kubectl get ns` xác nhận không còn namespace `nfk-17a`.
- Không còn nợ rollback.

## Review và tự giải thích

- **3 điều hiểu được:**
  1. `selector` của Service so khớp theo logic `AND` trên toàn bộ key-value; thừa hoặc sai lệch một nhãn sẽ khiến toàn bộ Pod bị loại trừ.
  2. Bắt bệnh Service rỗng endpoints luôn đi theo quy trình 3 bước: Check triệu chứng -> Control test trực tiếp Pod IP -> So sánh `spec.selector` với `metadata.labels` của Pods.
  3. Khi EndpointSlice rỗng, kube-proxy iptables phản hồi `REJECT` tức thì (0 ms, `Connection refused`), không để client chờ đợi timeout.
- **2 điều còn thắc mắc:**
  1. Nếu một Pod có `ReadinessProbe` bị fail, trong `kubectl get endpointslice` Pod đó sẽ hiển thị ra sao? (Sẽ quan sát ở các bài sau).
  2. Tại sao kube-proxy lại chọn REJECT thay vì DROP khi Service không có backend? (Vì REJECT giúp client fail-fast, biết ngay không có backend để kích hoạt cơ chế fallback/retry thay vì treo cả luồng xử lý do Timeout).
